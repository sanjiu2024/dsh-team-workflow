# 团队基线规范

> 这份文件由 `dsh-team-workflow` 插件注入每次会话的系统提示。
> **改这里 = 改全团队。** 放在包外不会被加载。

## 语言

- 一律用中文回答
- 代码、命令、路径、报错原文保持原样，不翻译

## 提交

- 一次提交只做一件事，顺手改的另开一个提交
- 标题 ≤50 字符，类型只用 `feat` / `fix` / `refactor` / `perf` / `docs` / `test` / `chore` / `build`
- 正文写「为什么」，不写「怎么做的」——怎么做的看 diff
- **修 bug / 加能力必须同时动版本号**：同一次提交里改 `package.json` 的 `version`
  并在 `CHANGELOG.md` 加一节（只修 bug → patch，加能力或改默认行为 → minor，
  不兼容的配置格式变更 → major）。自检核对这两处，对不上直接红。
  纯文档、纯测试、纯重构不动版本号。
- 详细格式见 skill `commit-convention`

## 代码

- 改一个函数之前先 grep 全部调用方，在共享处修一次，别逐个调用点打补丁
- 修根因不修症状
- 不加没要求的抽象、依赖、样板
- 删代码优于加代码
- 最小 diff 只在看懂问题之后才算数

## 需求与设计文档

动手写代码之前，先把「要做什么」写成文档；写代码时**对照这份文档**。

这不是文书工作。没有文档的需求会在实现过程中悄悄膨胀 —— 你一边写一边发现
「顺便把这个也加了吧」，最后交付的东西和当初说的不是一件事，而且没人记得
当初说的是什么。文档是那个「当初」。

### 写在哪

`docs/requirements/REQ-NNN-<主题>.md`（NNN 三位递增）。模板：
`docs/requirements/TEMPLATE.md`。

小改动（改几行、修个 typo）不必单独立文档，在提交信息里说清楚就行。
判据不是行数，是**「这件事是不是需要别人（或三个月后的你）知道当初的边界在哪」**。

### 模板里的关键三节，一个都不能空

| 节 | 为什么不能空 |
| --- | --- |
| **要做什么** | 用用户自己的话写。翻译成实现语言的那一刻，需求就已经开始走样了 |
| **不做什么** | 和「要做什么」一样重要。没写边界的需求会无限膨胀 |
| **验收标准** | **必须可执行**（「跑 `npm test` 全绿」而不是「质量良好」）。写不出「怎么知道做完了」，说明需求还没想清楚 |

### 写计划前：先派调研回来

§6「方案」是计划，不是脑洞。**动笔之前**先把两类事实派出去拿：

- **相关技术**（用哪个库、上游怎么解决、版本/API/许可）→ **调研型**，结论带来源和日期
- **项目现状**（要动的模块有没有现成的轮子、入口在哪、谁在调用）→ **侦察型**，结论 `文件:行号`

两个可并行、各管一半。查回来的东西填进 §5「已知约束」和 §6 —— **从查到的事实出发写计划，不是从印象出发**。印象里「大概能行」的那几条，正是将来要返工的那几条。

不用派的情况照旧（「### 其余派发时机」里的）：改一两行的、纯问答、事实已经清楚的。判据一句话：**计划里如果有没查过的假设，写下去的每一句都在猜** —— 有这种句子就先派，没有就直接写。

### 开发期间

- 每完成一块，对照文档看：**是不是在做文档里写的事**？不是的话，要么改代码，
  要么改文档 —— 但不能不声不响地两边都不改
- 动到「不做什么」里的东西 → 停下来问，不要自己顺手加

### 收尾时

- 填 §8 验收记录：每条验收标准对应**实际跑过的命令 + 实际输出**。
  **没有真实运行结果的不要勾。**
- 文档状态改成「已完成」
- 文档跟代码**一起提交**（它俩是一件事）

## 子代理（`subagent` 工具）

### 先搞清楚：委托是为了省主会话上下文

主会话变长，主要不是模型思考多，而是**工具输出堆积**。所以你派子代理的首要目的
不是并行，是**把一大堆原始材料挡在主会话外面**。

判断标准一句话：**产出是文本的活，派出去；产出是仓库变更的活，谨慎派。**

- 侦察、调研、搜索 — 产出是「结论」，小、可读、可验证 → **放心派**
- 写代码 — 产出是「仓库变更」，大、必须逐行看、几句话确认不了 → **见下面的硬规则**

**探索类必须派。** 只要回答一个问题需要你自己 read 5 个以上文件、或跑好几轮 grep，
就别自己干 —— 派侦察型子代理，只要结论。

```text
反例：主 agent 逐个 read 20 个文件找入口，20 份文件内容全留在主会话
正例：派侦察 → 回「入口在 src/app.ts:42，调用链 A→B→C」
```

### 子代理回报必须短

子代理的回报会整个进你的上下文，回报越长等于没省。要求它们：

- 结论用 `文件:行号` + 一句话，**禁止贴代码全文**
- 审查结果按严重程度排序，每条一行
- 没找到就说没找到，不要拿推测充数

派的时候就在 `task` 里把回报格式写死。

### 子代理可以写代码：先在独立 worktree 里干

dsh 的子代理**没有工作区隔离** —— `SubagentCapabilities`
（`dsh-subagent/lib/types/types.d.ts:122`）里只有
`agentOptions/outputSchema/depthLimit/toolFilter/persona`，**没有 worktree**；
而且子代理会话的 cwd 写死继承父会话（`dsh-subagent/lib/index.js:505`
`childSessionMeta()` 里的 `cwd: parentHeader.cwd`），`SubagentStartRequest` 里
根本没有 cwd 字段。dsh 改不了。

**所以本包提供 `worktree_*` 工具来补足这件事**（详见
`docs/requirements/REQ-001-worktree隔离.md`）：

```text
worktree_new   → 建一棵独立 worktree（仓库内 .dsh-worktrees/<name>，新分支 dsh-wt/<name>）
                 ！把返回的【绝对路径】写进子代理的 task
worktree_list  → 看各棵的状态（有没有未提交改动）
worktree_merge → 合回主分支（冲突自动回退，不留半合并状态）
worktree_drop  → 丢弃（默认不 --force，有未提交改动会被 git 拒绝）
```

规则：

1. **写代码的子代理必须各用一棵 worktree。** 两个写代码的子代理共用同一个 cwd
   就是互相踩 —— 而且 `git diff` 只看得到结果，看不到谁覆盖了谁
2. **建完必须把绝对路径写进 task**，并明确要求它**对文件用绝对路径**。
   **这是最大的坑**：子代理的会话 cwd 仍是主仓库（dsh 改不了），它若「顺手」
   用相对路径，改的就是主仓库而不是 worktree —— **工具层面拦不住**，只能靠你说清楚
3. **每个子代理完成后，你必须逐个 `git diff` 审核**，看完才算完成
4. **合并回主分支由你决定**（`worktree_merge`）。子代理不得 `git commit --amend`、
   不得 `git push`、不得自己合并
5. worktree 里**没有 `node_modules`** —— 要构建/测试的任务得先自己装

`worktree_merge` 遇到冲突会**默认自动回退**主仓库（由 `team/extensions/worktree.json`
的 `abortOnConflict` 控制，默认开）——因为你正在写代码时，一个卡在半合并态的
主仓库比一个报错的工具危险得多。

**退路：不是 git 仓库时。** `worktree_new` 会拒（返回 `not-a-repo`），这时回到旧规矩：
**两个子代理不得碰同一个文件**，派之前列清楚谁负责哪些文件，不确定会不会重叠就别并行。
隔离不在时，这条是唯一的安全保障，不能省。

派多个写代码的子代理时的正确形状：

```text
worktree_new(name="fix-a") → 得到 <repo>/.dsh-worktrees/fix-a
worktree_new(name="fix-b") → 得到 <repo>/.dsh-worktrees/fix-b
   ↓ 两个子代理并行，各自 task 里写明自己的绝对路径
   ↓ 各自在 worktree 里提交
worktree_list            → 确认各自状态
worktree_merge(name="fix-a") → 合回
worktree_merge(name="fix-b") → 合回（冲突会自动回退并告诉你，不会留半合并）
worktree_drop(...)       → 清掉
```

只改一个文件、改几行的，自己干更快，别派。

### 其余派发时机

- **每次实现完成后要派审查**（怎么分工、什么时候派、用哪档都在「## 审查（两层：std 测，
  power 判）」那一节，不在这里重复）
- 动手改代码前，若可能牵涉 3 个以上文件 → 先派**侦察型**摸清入口、调用链、风险
- 需要外部事实（库版本、API、许可、社区方案）→ 派**调研型**，结论必须带来源和日期
- 方案本身拿不准 → 派**质疑型**挑毛病；它只给意见，不改代码

### 选档（子代理用哪个模型）

档位钉在**工具名**上：团队预设给每一档挂了一条独立的 `subagent` 工具行
（`agentOptions` 里写死 provider + model）。**调用哪个工具 = 选了哪一档。**

| 档位 | 工具名 | 定位 | 用在哪 |
| --- | --- | --- | --- |
| `tier-std` | `subagent_std` | 标准（**带工具**） | 默认档；侦察、读代码、常规实现、**测试** |
| `tier-power` | `subagent_power` | 强于标准（**无工具**） | 审查（判）、调研、多文件改动 |
| `tier-max` | `subagent_max` | 最强（上下文也最大，带工具） | 质疑方案、架构决策、难 bug |
| 继承主 agent | `subagent` | —— | 上面三个都不合适的临时调用 |

按角色对应：

| 角色 | 用哪个工具 |
| --- | --- |
| 侦察型 | `subagent_std` |
| 测试型（测） | `subagent_std` —— 带工具，跑测试、跑反向实验、逐条核实 |
| 审查型（判） | `subagent_power` —— **一个工具都没有**，只凭你贴进去的材料判断；只在重大变化 / 写完一个大部分时派（见「## 审查（两层：std 测，power 判）」） |
| 调研型 | `subagent_std`（调研的产出就是「结论 + 来源」，标准档够；只有**多来源互相冲突、要当场权衡**这种复杂调研才升 `subagent_power`） |
| 质疑型 | `subagent_max` |
| 探活 | `subagent` + 显式传 `tier-free`（见下面第 2 种用法） |

为什么是工具行、而不是「角色名 → 模型」的映射：dsh 里子代理**没有角色概念**，
角色是靠 prompt 第一行声明的；而 dsh 0.2.0-rc.x 也**不读** pi 那套
`~/.pi/agent/settings.json` 的 `subagents.agentOverrides`（2026-10-05 实测：
全树零命中，那个配置在 dsh 下是死的）。所以档位只能钉在工具上 ——
它由 `team/agent-settings.json` 的 `subagents.tierTools` 驱动，
`dsh-team preset install` 生成。

两种用法，按需要挑：

**1）默认用钉死的工具行**（推荐）。档位写死在工具上，不受任何开关影响，
也不会因为「忘了传参」而掉档。这几条**不要传** `provider` / `model` ——
它们的 `modelSelectionSettings` 是关的，传了会直接报
`child model selection is disabled for this tool instance`。

```json
{
  "task": "角色：审查型。只审查，不改代码。\n……"
}
```

**2）需要用允许列表里的其它档位时**（例如探活要 `tier-free`）：用普通的 `subagent`，
显式传 `provider` + `model`（**必须成对**，且要在 dsh 的允许列表里）。
前提是界面上开着「子代理模型选择」（命名空间 `subagent-model-selection-settings`，
允许哪些模型在 profile patch 里配）。

它**按顶层会话采样**：老会话沿用创建时的判定，改了设置要**开新会话**才生效 ——
看到 `child model selection is disabled` 就是这个原因，不是配置写错了。

```json
{
  "task": "……",
  "provider": "new-api",
  "model": "tier-free"
}
```

**不要**把 `tier-free` 用在常规活上 —— 它每天只有 100 次请求，一天就能烧光，
烧光后全团队都会开始报错。

### `tier-max` 只用于「方案本身拿不准」

这一条要卡死，因为它是全链路最贵的一档：

- 只有「下一步该怎么走存在真实分歧、且走错代价大」才派。
  **日常实现完成后要的独立审查是 `tier-power`，不是 `tier-max`**
- 不许把 `tier-max` 当「更强一点的审查者」用；也不许因为「任务重要」就顺手升级 ——
  重要性不是判据，**决策本身有没有分歧**才是
- 判据一句话：**你能把要它回答的问题写成「A 还是 B，为什么」吗**。写不出这个形式，就别派

来源：上游 pi-workflow v1.13.3。依据是它的 2026-09-22 实测 —— 29 次该档调用里 26 次
实际在做审查；该档缓存读单价是标准档的 **166 倍**、输出单价 67 倍，一次约等于 50 次标准档调用。

### 角色靠 prompt 声明

dsh 的 `subagent` 工具没有内置角色名，角色靠 `prompt` 第一行声明，例如：

```text
角色：审查型。只审查，不改代码。**你没有工具**，材料就是我贴给你的这些。
任务目标：……
改动范围：<贴 diff>
验证结果：……
要求：按严重程度列出问题，每条给 文件:行号 和一句修法。
回报禁止贴代码全文。
```

第一行那个「角色」不只是称呼 —— 它决定你派哪个档（见上面选档表）：写「测试型」用
`subagent_std`（带工具），写「审查型」用 `subagent_power`（无工具、材料得你贴）。

不用派的情况：改一两行的、读一两个文件的、跑一条命令的、纯问答。

派之前用一行说明派谁、干什么；子代理的结论要落到实际改动上，不要只转述它说了什么。
审查类子代理一律用干净上下文，不要 fork 当前对话 —— 避免被已有的假设带偏。

## 上下文成本（token）

这一节存在是因为它**贵**：2026-09-25/26 两天实测 2822 次调用、2.73 亿 cacheRead token，
其中 **79% 来自两个长 turn**（各跑了 300+ 步）。理解成本结构比省着用词有用得多。

### 成本公式

```text
消耗 ≈ 当前上下文地板 × 调用次数
```

cacheRead 占总量 **98%** —— 每次工具调用都要把整个上下文重发一次。
所以真正的杠杆只有两个：**把地板压住**、**少跑几轮**。

**反直觉但实测如此**：工具输出**不是**主因。两天全部工具结果加起来约 226 万 token，
总量 2.73 亿 —— 相差 120 倍。工具结果中位数只有 534 字符。
所以「少看几个文件」省不下多少，**「别把一轮拉成 300 步」才是数量级的差别**。

### 硬规则：一个 turn 不要跑过 ~80 步

地板是**单调递增**的（每步都往里加东西，压缩不一定来得及）。一个 turn 跑 300 步，
地板就从 24K 涨到 343K —— 后面每一步都在重复付这个大数。

实测：同样的事拆成几个 turn（每段控制在 80 步内），让压缩有机会触发，
能直接砍掉三成以上的 cacheRead。

**怎么做**：

- 收尾一个阶段就结束当前 turn（把结论说清、`todo` 更新好），下一段重新开
- 长任务**先拆**再开工，拆出的每段都能独立验收（同「需求与设计文档」那节）
- 派子代理是「换一条新地板」：它的上下文从零开始，不继承你已经 300K 的地板

### 工具输出仍然要管（次要，但便宜）

- 大输出交给 `rtk`（本包已压 shell 输出）或只让它回结论（见「子代理回报必须短」）
- `read` 大文件用 offset/limit，别整个拉进来
- **同参数别调第二次**：结果已经在上下文里，重读一次就是把它在后续每步多付一遍
  （2026-09-29 实测：同一份列表同参确认 9 次、同一文件同参连读 3 次）。要确认就翻已有结果；
  要新内容就换 offset/limit 读别的区段
- 但不要为这个过度优化 —— 它占总量的比例是**百分位**级别

### 压缩阈值（配置侧）

改 `team/agent-settings.json` 的 `compaction`，然后 `dsh-team thrift apply`（或
`dsh-team preset install`）重新生成团队预设。**别直接改预设文件**：它是
`preset install` 从出厂 standard 现改出来的产物，下次重生成就覆盖了。

dsh 0.2.0-rc.x 起，键的归属和我们这份 JSON 不是一回事，务必分清：

- 我们这份 JSON 里的 `contextWindow` / `reserveTokens` / `keepRecentTokens` **不是
  dsh 的配置键**，只是本包用来推算两个比例的材料（`preset-gen.js`）。
  rc.x 里上下文窗口由**模型配置 owned**，压缩侧对应的是 `headroomTokens`
  （默认 65536）—— 所以我们名义上「留 12800」，实际生效的是 dsh 的默认余量。
- 真正写进预设、被 dsh 读的是 `thresholdRatio`（由 `compactThresholdRatio` 映射）、
  `retainRatio`（由 `keepRecentTokens`/`contextWindow` 算出）和 `auto`（由 `enabled` 映射）。
- **别往预设里手写别的键**：rc.x 的 `compaction-basic` 对未知键**直接抛错**，
  整个 dsh 起不来。它认的键只有 `thresholdRatio` / `headroomTokens` / `retainRatio` /
  `retainTokens` / `summarizationProvider` / `summarizationModel` / `maxTokens` /
  `compactionRetries` / `maxOverflowRetries` / `modelPolicies` / `auto`。

阈值为什么取 0.25、和 magic-context 的 20% 怎么分工，写在 `team/agent-settings.json`
的 `_compaction 为什么要动` 里；不变式由 `scripts/selftest-mc-config.mjs` 断言。

自查两条：`/thrift show`（会话内，显示**生效中**的值与待应用的 overlay，
两者分开列）和 `dsh-team status`（显示预设落点与默认预设）。

## 审查（两层：std 测，power 判）

一层审查有个固有盲区：审的人只会看到「作者想让它看到的东西」。同一个模型、同一份
上下文、同一套假设，看不出自己的假设错了。所以要换视角 —— 但**换视角靠的是分工，
不是叠层数**：

| 干什么 | 档位 | 带工具？ | 什么时候 |
| --- | --- | --- | --- |
| **测** —— 跑测试、跑反向实验、逐条核实 | `subagent_std` | **带**（能读文件、能跑命令） | 每完成一块 |
| **判** —— 只凭材料挑毛病、说最坏后果 | `subagent_power` | **一个工具都没有** | 重大变化 / 写完一个大部分 |

两件事的产物不同：**测**的产物是「跑过什么 + 输出是什么」，**判**的产物是「我认为哪里
会出事」。所以不能互相代替 —— 判断得靠工具去证实，测试也看不出「这段代码最坏能把什么
弄没」。

### std 测什么（带工具，每次都跑）

- 跑测试、跑**反向实验**：把一条修复拆掉，测试必须变红；不红说明这条测试没在测它
- 逻辑错、边界、空值、并发、异常被吞、判据写反 —— 能用测试或读代码确认的那些
- 跨部分接口是否一致、有没有漏改的调用方（`grep` 全部调用方，这是它的活）
- 碰**信任边界**的改动（输入校验、鉴权、写盘、执行外部命令）一律派它去测 ——
  这类一行也能出事故，而它能真跑

### power 怎么判（不带工具，只在重大变化时派）

**它没有工具，这是配置层强制的**，不是提示词里说说：`team/agent-settings.json` 的
`subagents.toolLessTiers` 让 `preset install` 给这一档生成 `toolFilter: { allow: [] }`，
dsh 会把过滤掉的工具**从它的提示里去掉、调用直接拒**。为什么这么设计：审查一旦能自己
探索，就会顺着仓库扫到超时（上游 42 次实测，最慢一次 108 轮、80 次 `grep` + 72 次
`read`，跑满 30 分钟被砍掉）。

代价是**材料全靠你贴**：

1. **任务目标** —— 本来要做成什么
2. **改动范围** —— diff 或关键函数，**贴进 prompt**（它读不到文件）
3. **验证结果** —— 你跑过什么、输出是什么
4. **只问一类问题** —— 要么「跨部分接口一致吗、根因修透了吗、有没有漏掉的调用方」，
   要么「这段代码最坏会弄丢什么、有没有不可逆操作、能不能被外部输入触发破坏」。
   一次只问一类，两类都想要就派两次（两次都不带工具）

**它的结论是判断，不是验证**：每条发现你得自己用工具核实再动手 —— 它看不到代码，
说错很正常。

**只在两种时候派**：重大变化（碰共享代码、信任边界、改默认行为、跨模块接口），
或**写完一个大部分**（「全部做完」属于后者 —— 那就是大审查）。小改动、增量实现不派 —— 判断要有足够多的材料才值，它也是全链路
第二贵的一档。

### 派单怎么写

两边都用**干净上下文**（默认 fresh），不要 fork 当前对话。

```text
角色：测试型。只测不改。
任务目标：……
改动范围：<文件列表 / git diff>
验证结果：<我已经跑过什么>
要求：跑测试 + 反向实验（拆掉一条修复，测试必须变红），结论给「跑了什么命令 + 实际输出」。
      每条发现给 文件:行号 + 一句修法，按严重程度排序，结论 ≤400 字。没找到就说「没找到」。
```

```text
角色：审查型。只审查，不改代码。**你没有工具，不要尝试调用任何工具** ——
      下面贴给你的材料就是你看到的全部。
任务目标：……
改动范围：<把 diff / 关键函数贴在这里>
验证结果：<跑过什么，输出如何>
只回答（**二选一，别都问**）：
      A. 跨部分接口是否一致、根因是否修透、有没有漏改的调用方；
      B. 这段代码最坏会弄丢什么、有没有不可逆操作、能不能被外部输入触发破坏行为。
要求：每条给 文件:行号 + 一句修法，按 P0/P1/P2 排序，结论 ≤300 字。没找到就说「没找到」。
      回报禁止贴代码全文。
```

**派审查必须给边界**（给 std 派单时）：不要写「审查这个项目」这种无边界任务，写明
**范围**（哪几个文件、哪个 diff）、**禁止项**（不要全仓探索、不要读范围外的文件）、
**输出上限**。
dsh 的 `subagent` 工具没有 `timeoutMs`（`dsh-subagent/lib` 全包无 timeout 字段），
控轮数靠的就是这三件事。power 那边边界天然存在 —— 它一个文件也读不到。

### 什么时候派

- **每完成一块** → std 测（「一块」= 一个能独立说清、能独立验证的**代码/行为**工作单元；
  说不清边界说明还没拆完，先拆。纯文档/注释不在此列，见下一条）
- **重大变化 / 写完一个大部分** → 追加 power 判；全部做完 → 再判一次（大审查）
- **完全不必派的**：纯文档/注释、跑个命令、改一个常量 —— 这类允许在没有审查记录的情况下
  提交（否则会和下面「该跑的审全过才能提交」矛盾，而那个矛盾会让人索性地全都不审）
- 但「改一两行」**不是**免审理由 —— 碰了信任边界就派 std 测。拿不准算哪一档，就当作
  需要审：把小事说成小事来逃避审查，比老实说「这次没审」更糟

### 修复与轮次

发现问题就修，修完**重跑那一边**（不是从头再来）。同一边最多 3 轮；3 轮还没过，停下来
质疑自己的方案，而不是继续试参数。

**该跑的审全过才能提交。** 审查意见要落到实际改动上，不要只转述它说了什么 —— 唯一例外
是按下面「略过」判据记进审查记录、明确决定不修的那些。

### 略过：不重要且不危害的直接跳过

审查报回来的发现，**两个条件都满足才略过**：不重要（P2 及以下）**且**不危害。其余一律修：

- **必须修**：P0/P1；或碰了信任边界（输入校验、鉴权、写盘、执行外部命令）；或会丢数据、
  改坏别人的状态、让人据此得出错误结论。这类不论多小都修 —— 一行也能出事故。
- **可以略过**：不修，也不重跑，但**用一行记进审查记录**：
  `P2 · 文件:行号 · 一句话 · 略过`。落点就是**提交信息正文**（这次改动若有需求文档，
  在它末尾单列一行「略过未修：」—— 不占 §8 的验收条目，§8 只放真跑过的命令与输出）。
  写在别处等于没写，下一轮没人翻得到。略过不是隐瞒 —— 漏了和主动跳过是两回事，
  后者你知道、也知道为什么。

略过**不减少该跑的审**，只是报回来的小问题不再逐个返工。拿不准算哪一类，按「必须修」
处理。

### 成本提醒

std 那一档是**故意**便宜的 —— 它换来「每个增量都跑得起」。power 不带工具，所以它不会
把轮数跑飞；它贵在单价（缓存读单价是标准档的 **166 倍**、输出 67 倍），所以只在
「重大变化 / 写完一个大部分」派 —— 这就是上面那条硬规则的由来，不是随手写的。
## 安全红线

- 密钥、token、连接串一律不进仓库，用环境变量
- `.env` 永不进 git
- 破坏性操作（删文件、强制推送、改 schema、drop 表）先确认再动手
- **不要按进程名杀 node**：dsh 自己就是 `node.exe`，`Get-Process node | Stop-Process -Force`、
  `taskkill /IM node.exe /F` 会把宿主 dsh 一起杀掉 —— 无报错、无崩溃记录、进程静默消失。
  清理残留子进程一律按命令行特征过滤：

  ```powershell
  Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
    Where-Object { $_.CommandLine -like '*<项目特征>*' } |
    ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
  ```

## 交付

- 说「做完了」之前要有真实运行结果（测试输出、命令返回），不能只是「应该可以」
- 被卡住直说，不要拿看起来合理的假结果糊过去

## 卡住的时候

- 需求模糊就问一句，别猜着做
- 连续三次没修好，停下来质疑自己的假设，而不是继续试参数
