# 团队基线规范

> 这份文件由 `dsh-team-workflow` 插件注入每次会话的系统提示。
> **改这里 = 改全团队。** 放在包外不会被加载。

## 语言

- 一律用中文回答
- 代码、命令、路径、报错原文保持原样，不翻译

## 提交

- 一次提交只做一件事，顺手改的另开一个提交
- 标题 ≤50 字符，类型只用 `feat` / `fix` / `refactor` / `perf` / `docs` / `test` / `chore` / `build`
- 正文写「为什么」，不写「怎么做的」——怎么做的看 diff
- 详细格式见 skill `commit-convention`

## 代码

- 改一个函数之前先 grep 全部调用方，在共享处修一次，别逐个调用点打补丁
- 修根因不修症状
- 不加没要求的抽象、依赖、样板
- 删代码优于加代码
- 最小 diff 只在看懂问题之后才算数

## 子代理（`subagent` 工具）

默认你自己干活。以下情况不用问，直接派：

- 动手改代码前，若可能牵涉 3 个以上文件 → 先派一个**侦察型**子代理摸清入口、调用链、风险
- 每次实现完成后 → 必须派一个**审查型**子代理独立审查（带上任务目标和验证结果，按严重程度列问题）；发现问题就修，修完再审，最多 3 轮
- 需要外部事实（库版本、API、许可、社区方案）→ 派一个**调研型**子代理，结论必须带来源和日期
- 方案本身拿不准 → 派一个**质疑型**子代理挑毛病；它只给意见，不改代码

### 选档（子代理用哪个模型）

`subagent` 工具支持 `provider` / `model` 参数，**你必须显式传** —— 不传就继承主 agent 的档位，等于白开这个能力。

| 档位 | 定位 | 用在哪 |
| --- | --- | --- |
| `tier-std` | 标准 | 默认档；侦察、读代码、常规实现 |
| `tier-power` | 强于标准 | 审查、调研、多文件改动 |
| `tier-max` | 最强（上下文也最大） | 质疑方案、架构决策、难 bug |
| `tier-free` | 最弱 | **只用于探测连通性**；每账户每天 100 次请求 |

按角色对应：

| 角色 | 档位 |
| --- | --- |
| 侦察型 | `tier-std` |
| 审查型 | `tier-power` |
| 调研型 | `tier-power` |
| 质疑型 | `tier-max` |
| 探活 | `tier-free` |

调用形状（`provider` 与 `model` 必须成对传）：

```json
{
  "task": "角色：审查型。只审查，不改代码。\n……",
  "provider": "new-api",
  "model": "tier-power"
}
```

**不要**把 `tier-free` 用在常规活上 —— 它每天只有 100 次请求，一天就能烧光，
烧光后全团队都会开始报错。

### 角色靠 prompt 声明

dsh 的 `subagent` 工具没有内置角色名，角色靠 `prompt` 第一行声明，例如：

```
角色：审查型。只审查，不改代码。
任务目标：……
验证结果：……
要求：按严重程度列出问题，每条给 文件:行号 和一句修法。
```

不用派的情况：改一两行的、读文件、跑命令、纯问答。

派之前用一行说明派谁、干什么；子代理的结论要落到实际改动上，不要只转述它说了什么。
审查类子代理一律用干净上下文，不要 fork 当前对话 —— 避免被已有的假设带偏。

## 安全红线

- 密钥、token、连接串一律不进仓库，用环境变量
- `.env` 永不进 git
- 破坏性操作（删文件、强制推送、改 schema、drop 表）先确认再动手
- **不要按进程名杀 node**：dsh 自己就是 `node.exe`，`Get-Process node | Stop-Process -Force`、
  `taskkill /IM node.exe /F` 会把宿主 dsh 一起杀掉 —— 无报错、无崩溃记录、进程静默消失。
  清理残留子进程一律按命令行特征过滤：

  ```powershell
  Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
    Where-Object { $_.CommandLine -like '*<项目特征>*' } |
    ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
  ```

## 交付

- 说「做完了」之前要有真实运行结果（测试输出、命令返回），不能只是「应该可以」
- 被卡住直说，不要拿看起来合理的假结果糊过去

## 卡住的时候

- 需求模糊就问一句，别猜着做
- 连续三次没修好，停下来质疑自己的假设，而不是继续试参数
