# 团队基线规范

> 这份文件由 `dsh-team-workflow` 插件注入每次会话的系统提示。
> **改这里 = 改全团队。** 放在包外不会被加载。

## 语言

- 一律用中文回答
- 代码、命令、路径、报错原文保持原样，不翻译

## 提交

- 一次提交只做一件事，顺手改的另开一个提交
- 标题 ≤50 字符，类型只用 `feat` / `fix` / `refactor` / `perf` / `docs` / `test` / `chore` / `build`
- 正文写「为什么」，不写「怎么做的」——怎么做的看 diff
- 详细格式见 skill `commit-convention`

## 代码

- 改一个函数之前先 grep 全部调用方，在共享处修一次，别逐个调用点打补丁
- 修根因不修症状
- 不加没要求的抽象、依赖、样板
- 删代码优于加代码
- 最小 diff 只在看懂问题之后才算数

## 需求与设计文档

动手写代码之前，先把「要做什么」写成文档；写代码时**对照这份文档**。

这不是文书工作。没有文档的需求会在实现过程中悄悄膨胀 —— 你一边写一边发现
「顺便把这个也加了吧」，最后交付的东西和当初说的不是一件事，而且没人记得
当初说的是什么。文档是那个「当初」。

### 写在哪

`docs/requirements/REQ-NNN-<主题>.md`（NNN 三位递增）。模板：
`docs/requirements/TEMPLATE.md`。

小改动（改几行、修个 typo）不必单独立文档，在提交信息里说清楚就行。
判据不是行数，是**「这件事是不是需要别人（或三个月后的你）知道当初的边界在哪」**。

### 模板里的关键三节，一个都不能空

| 节 | 为什么不能空 |
| --- | --- |
| **要做什么** | 用用户自己的话写。翻译成实现语言的那一刻，需求就已经开始走样了 |
| **不做什么** | 和「要做什么」一样重要。没写边界的需求会无限膨胀 |
| **验收标准** | **必须可执行**（「跑 `npm test` 全绿」而不是「质量良好」）。写不出「怎么知道做完了」，说明需求还没想清楚 |

### 开发期间

- 每完成一块，对照文档看：**是不是在做文档里写的事**？不是的话，要么改代码，
  要么改文档 —— 但不能不声不响地两边都不改
- 动到「不做什么」里的东西 → 停下来问，不要自己顺手加

### 收尾时

- 填 §8 验收记录：每条验收标准对应**实际跑过的命令 + 实际输出**。
  **没有真实运行结果的不要勾。**
- 文档状态改成「已完成」
- 文档跟代码**一起提交**（它俩是一件事）

## 子代理（`subagent` 工具）

### 先搞清楚：委托是为了省主会话上下文

主会话变长，主要不是模型思考多，而是**工具输出堆积**。所以你派子代理的首要目的
不是并行，是**把一大堆原始材料挡在主会话外面**。

判断标准一句话：**产出是文本的活，派出去；产出是仓库变更的活，谨慎派。**

- 侦察、调研、搜索 — 产出是「结论」，小、可读、可验证 → **放心派**
- 写代码 — 产出是「仓库变更」，大、必须逐行看、几句话确认不了 → **见下面的硬规则**

**探索类必须派。** 只要回答一个问题需要你自己 read 5 个以上文件、或跑好几轮 grep，
就别自己干 —— 派侦察型子代理，只要结论。

```text
反例：主 agent 逐个 read 20 个文件找入口，20 份文件内容全留在主会话
正例：派侦察 → 回「入口在 src/app.ts:42，调用链 A→B→C」
```

### 子代理回报必须短

子代理的回报会整个进你的上下文，回报越长等于没省。要求它们：

- 结论用 `文件:行号` + 一句话，**禁止贴代码全文**
- 审查结果按严重程度排序，每条一行
- 没找到就说没找到，不要拿推测充数

派的时候就在 `task` 里把回报格式写死。

### 子代理可以写代码：先在独立 worktree 里干

dsh 的子代理**没有工作区隔离** —— `SubagentCapabilities`
（`dsh-subagent/lib/types/types.d.ts:122`）里只有
`agentOptions/outputSchema/depthLimit/toolFilter/persona`，**没有 worktree**；
而且子代理会话的 cwd 写死继承父会话（`dsh-subagent/lib/index.js:505`
`childSessionMeta()` 里的 `cwd: parentHeader.cwd`），`SubagentStartRequest` 里
根本没有 cwd 字段。dsh 改不了。

**所以本包提供 `worktree_*` 工具来补足这件事**（详见
`docs/requirements/REQ-001-worktree隔离.md`）：

```text
worktree_new   → 建一棵独立 worktree（仓库内 .dsh-worktrees/<name>，新分支 dsh-wt/<name>）
                 ！把返回的【绝对路径】写进子代理的 task
worktree_list  → 看各棵的状态（有没有未提交改动）
worktree_merge → 合回主分支（冲突自动回退，不留半合并状态）
worktree_drop  → 丢弃（默认不 --force，有未提交改动会被 git 拒绝）
```

规则：

1. **写代码的子代理必须各用一棵 worktree。** 两个写代码的子代理共用同一个 cwd
   就是互相踩 —— 而且 `git diff` 只看得到结果，看不到谁覆盖了谁
2. **建完必须把绝对路径写进 task**，并明确要求它**对文件用绝对路径**。
   **这是最大的坑**：子代理的会话 cwd 仍是主仓库（dsh 改不了），它若「顺手」
   用相对路径，改的就是主仓库而不是 worktree —— **工具层面拦不住**，只能靠你说清楚
3. **每个子代理完成后，你必须逐个 `git diff` 审核**，看完才算完成
4. **合并回主分支由你决定**（`worktree_merge`）。子代理不得 `git commit --amend`、
   不得 `git push`、不得自己合并
5. worktree 里**没有 `node_modules`** —— 要构建/测试的任务得先自己装

`worktree_merge` 遇到冲突会**默认自动回退**主仓库（由 `team/extensions/worktree.json`
的 `abortOnConflict` 控制，默认开）——因为你正在写代码时，一个卡在半合并态的
主仓库比一个报错的工具危险得多。

**退路：不是 git 仓库时。** `worktree_new` 会拒（返回 `not-a-repo`），这时回到旧规矩：
**两个子代理不得碰同一个文件**，派之前列清楚谁负责哪些文件，不确定会不会重叠就别并行。
隔离不在时，这条是唯一的安全保障，不能省。

派多个写代码的子代理时的正确形状：

```text
worktree_new(name="fix-a") → 得到 <repo>/.dsh-worktrees/fix-a
worktree_new(name="fix-b") → 得到 <repo>/.dsh-worktrees/fix-b
   ↓ 两个子代理并行，各自 task 里写明自己的绝对路径
   ↓ 各自在 worktree 里提交
worktree_list            → 确认各自状态
worktree_merge(name="fix-a") → 合回
worktree_merge(name="fix-b") → 合回（冲突会自动回退并告诉你，不会留半合并）
worktree_drop(...)       → 清掉
```

只改一个文件、改几行的，自己干更快，别派。

### 其余派发时机

- **每次实现完成后要派审查**（触发时机、分几层、用哪档都在「## 审查（三层）」那一节，
  不在这里重复）
- 动手改代码前，若可能牵涉 3 个以上文件 → 先派**侦察型**摸清入口、调用链、风险
- 需要外部事实（库版本、API、许可、社区方案）→ 派**调研型**，结论必须带来源和日期
- 方案本身拿不准 → 派**质疑型**挑毛病；它只给意见，不改代码

### 选档（子代理用哪个模型）

`subagent` 工具支持 `provider` / `model` 参数，**你必须显式传** —— 不传就继承主 agent 的档位，等于白开这个能力。

| 档位 | 定位 | 用在哪 |
| --- | --- | --- |
| `tier-std` | 标准 | 默认档；侦察、读代码、常规实现 |
| `tier-power` | 强于标准 | 审查、调研、多文件改动 |
| `tier-max` | 最强（上下文也最大） | 质疑方案、架构决策、难 bug |
| `tier-free` | 最弱 | **只用于探测连通性**；每账户每天 100 次请求 |

按角色对应：

| 角色 | 档位 |
| --- | --- |
| 侦察型 | `tier-std` |
| 审查型 | `tier-power`（普通审查都是这一档；**只有三层审查的第 1 层**例外用 `tier-std`，见「## 审查（三层）」） |
| 调研型 | `tier-power` |
| 质疑型 | `tier-max` |
| 探活 | `tier-free` |

注：`~/.pi/agent/settings.json` 里的 `subagents.agentOverrides.reviewer.model` 写的是
`tier-power`，但**显式传的 `model` 会盖过它**（2026-09-25 实测：传 `tier-std` 时
`message_start` 里确实是 `tier-std`）。所以第 1 层不需要为了绕过覆盖而改全局设置。

调用形状（`provider` 与 `model` 必须成对传）：

```json
{
  "task": "角色：审查型。只审查，不改代码。\n……",
  "provider": "new-api",
  "model": "tier-power"
}
```

**不要**把 `tier-free` 用在常规活上 —— 它每天只有 100 次请求，一天就能烧光，
烧光后全团队都会开始报错。

### `tier-max` 只用于「方案本身拿不准」

这一条要卡死，因为它是全链路最贵的一档：

- 只有「下一步该怎么走存在真实分歧、且走错代价大」才派。
  **日常实现完成后要的独立审查是 `tier-power`，不是 `tier-max`**
- 不许把 `tier-max` 当「更强一点的审查者」用；也不许因为「任务重要」就顺手升级 ——
  重要性不是判据，**决策本身有没有分歧**才是
- 判据一句话：**你能把要它回答的问题写成「A 还是 B，为什么」吗**。写不出这个形式，就别派

来源：上游 pi-workflow v1.13.3。依据是它的 2026-09-22 实测 —— 29 次该档调用里 26 次
实际在做审查；该档缓存读单价是标准档的 **166 倍**、输出单价 67 倍，一次约等于 50 次标准档调用。

### 角色靠 prompt 声明

dsh 的 `subagent` 工具没有内置角色名，角色靠 `prompt` 第一行声明，例如：

```text
角色：审查型。只审查，不改代码。
任务目标：……
验证结果：……
要求：按严重程度列出问题，每条给 文件:行号 和一句修法。
回报禁止贴代码全文。
```

不用派的情况：改一两行的、读一两个文件的、跑一条命令的、纯问答。

派之前用一行说明派谁、干什么；子代理的结论要落到实际改动上，不要只转述它说了什么。
审查类子代理一律用干净上下文，不要 fork 当前对话 —— 避免被已有的假设带偏。

## 审查（三层）

### 为什么分三层，而不是让一个更强的模型审一遍

一层审查有个固有盲区：审的人只会看到「作者想让它看到的东西」。同一个模型、同一份
上下文、同一套假设，看不出自己的假设错了。

**分层不是为了更严格，是为了换三个不同的视角。** 每层负责不同类别的错，前一层没过
不要开下一层（后面的层假设前面已经干净了，带着已知的错误往下审是浪费）。

| 层 | 视角 | 档位 | 专抓 |
| --- | --- | --- | --- |
| 1 | 正确性 | `tier-std` | 逻辑错、边界、空值、并发、异常被吞、判据写反 |
| 2 | 整体性 | `tier-power` | 跨部分接口不一致、根因没修透、与既有约定冲突、漏掉的调用方 |
| 3 | 安全 / 破坏性 | `tier-power` | 丢数据、越权、注入、破坏性操作、密钥进仓库、不可逆副作用 |

第 3 层**不是「更严的第 2 层」**，它问的是完全不同的问题：「这段代码最坏能把什么
弄没？」所以不能拿第 2 层的结果代替。

### 什么时候跑哪几层

- **每完成一部分** → 跑第 1 层。若这部分改了共享代码或跨模块接口 → 追加第 2 层。
- **全部做完** → 三层全跑一遍（大审查）。
- **碰了信任边界的小改动** → **只跑第 3 层**（跳过前两层，但不能不审）。
  信任边界指：输入校验、鉴权、写盘、执行外部命令。这类改动一行也能出安全事故，
  而第 1/2 层的视角（逻辑、接口）对小改动没多少可看的。

「一部分」指一个能独立说清、能独立验证的工作单元（一个功能、一个修复、一次重构）。
说不清边界，说明还没拆完，先拆。

**完全不必派的情况：**纯文档/注释的、跑个命令的、改一个常量的。
这类改动允许在没有审查记录的情况下提交（否则会和「该跑的层全过才允许提交」矛盾，
而那个矛盾会让人索性地全都不审）。

但「改一两行」**不是**免审理由 —— 它会走向上面「只跑第 3 层」那一档。
拿不准算哪一档，就当作需要审。把小事说成小事来逃避审查，比老实说「这次没审」更糟。

### 每层怎么派

三层都用**干净上下文**（默认 fresh），不要 fork 当前对话。每次只给三样东西：

1. **任务目标** —— 本来要做成什么
2. **改动范围** —— `git diff` 或具体文件，别让审的人自己找
3. **验证结果** —— 你已经跑过什么、结果如何（自检、真实运行输出）

然后**只问这一层的那个问题**。不要把三个层的问题塞进一个 prompt —— 那会变成
一个泛泛的「帮我看看」，等于没分层。

```text
角色：审查型。只审查，不改代码。
层次：第 1 层（正确性）。
任务目标：……
改动范围：<文件列表 / git diff>
验证结果：<跑过什么，输出如何>
只回答：逻辑错、边界、空值、并发、异常被吞 —— 这几类里有没有问题。
要求：每条给 文件:行号 + 一句修法，按严重程度排序。没找到就说「没找到」。
回报禁止贴代码全文。
```

第 2 层把「只回答」换成：跨部分接口是否一致、有没有漏改的调用方、根因是否修透、
有没有和团队既有约定冲突。

第 3 层把「只回答」换成：这段代码最坏会弄丢什么/改坏什么；有没有信任边界缺少校验；
有没有不可逆操作、越权、注入、密钥；能不能被外部输入触发出破坏行为。

### 修复与轮次

发现问题就修，修完**重跑该层**（不是从第 1 层重来）。同一层最多 3 轮；
3 轮还没过，停下来质疑自己的方案，而不是继续试参数。

**跑过的层全过才能提交。** 哪些层该跑由上面「什么时候跑哪几层」定 ——
所以「改一两行」或「只碰了信任边界（那样只跑第 3 层）」也能直接提交，
前提是它们该跑的层都过了。

审查意见要落到实际改动上，不要只转述它说了什么。

### 成本提醒

第 1 层用 `tier-std` 是**故意**的 —— 它靠便宜换来「每个增量都跑得起」。
这是唯一一处把审查降到 `tier-std` 的例外（档位表与选档规则见上）。

## 安全红线

- 密钥、token、连接串一律不进仓库，用环境变量
- `.env` 永不进 git
- 破坏性操作（删文件、强制推送、改 schema、drop 表）先确认再动手
- **不要按进程名杀 node**：dsh 自己就是 `node.exe`，`Get-Process node | Stop-Process -Force`、
  `taskkill /IM node.exe /F` 会把宿主 dsh 一起杀掉 —— 无报错、无崩溃记录、进程静默消失。
  清理残留子进程一律按命令行特征过滤：

  ```powershell
  Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
    Where-Object { $_.CommandLine -like '*<项目特征>*' } |
    ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
  ```

## 交付

- 说「做完了」之前要有真实运行结果（测试输出、命令返回），不能只是「应该可以」
- 被卡住直说，不要拿看起来合理的假结果糊过去

## 卡住的时候

- 需求模糊就问一句，别猜着做
- 连续三次没修好，停下来质疑自己的假设，而不是继续试参数
