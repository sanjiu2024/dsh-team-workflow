# 从需求到发布：工作流

按顺序走。规范原文（规则、边界、选档）以 `team/RULES.md` 为准，这里只给**顺序和判据**——
两处冲突时以 RULES.md 为准，并把冲突当场告诉用户。

每步都标了**产出**和**过关判据**。判据没过，就不进下一步。

## 0. 先判定：这活要不要走全流程

- 改一两行、修 typo、跑个命令、纯问答 → **不走**，直接干，提交信息说清楚
- 「别人（或三个月后的你）需要知道当初的边界在哪」→ 走全流程

## 1. 理清需求 → 写 REQ 文档

**用户原话含糊就先问，别猜着做。** 问完写 `docs/requirements/REQ-NNN-<主题>.md`
（模板 `docs/requirements/TEMPLATE.md`，NNN 递增）。

三节一个都不能空：

| 节 | 写什么 |
| --- | --- |
| 要做什么 | 用户自己的话，不翻译成实现语言 |
| 不做什么 | 边界，防止做着做着膨胀 |
| 验收标准 | **可执行的检查**，不是「质量良好」 |

**过关判据**：不看对话历史，只读这份文档就能回答「做完了怎么知道」。

## 2. 写计划前：先派调研回来

计划里的每一个「改 A 就行」都得是查过的事实，不是印象。

- 相关技术（库/API/许可/上游方案）→ 派**调研型**，结论带来源和日期
- 项目现状（入口、调用链、有没有现成轮子）→ 派**侦察型**，结论 `文件:行号`
- 两个可并行，各管一半；结论填进 REQ §5 已知约束

**过关判据**：§6 方案里没有「大概能行」——有没查过的假设，那句话就是猜的。
改一两行、事实已经清楚的，跳过这步直接写。

## 3. 实现（对照 REQ 写，不对照记忆写）

- 动手前把 §6 方案过一遍：改哪些文件、为什么走这条路
- **写代码派子代理时**：`worktree_new` 各给一棵 worktree，**绝对路径写进 task**；
  完事 `worktree_merge` 合回。不给 worktree 的话两个子代理在同一个 cwd 互相踩
- 实现期间发现要做「不做什么」里列的事 → 停，问用户，不顺手加
- 改了共享函数 → 先 grep 全部调用方，在共享处修一次

**过关判据**：改动都能指着 REQ 的某一节说「这是它要的」。

## 4. 审查（两层：std 测，power 判）

- 每完成一块 → **std 测**（`subagent_std`，带工具）：跑测试 + 反向实验（拆掉一条修复，
  测试必须变红）+ grep 全部调用方
- 只碰信任边界的小改动 → 也派 std 测（一行也能出事故）
- **重大变化 / 写完一个大部分** → 追加 **power 判**（`subagent_power`，**一个工具都没有**）：
  材料（diff / 关键函数 / 验证结果）得**贴进 prompt**，它读不到文件；它的产物是判断，
  每条发现自己用工具核实再动手
- 全部做完 → 再判一次（大审查）

派审必须给**边界**（范围/禁止项/输出上限），模板见 RULES.md「审查（两层）· 派单怎么写」。
发现问题就修，修完**重跑那一边**，同一边最多 3 轮。

**过关判据**：该跑的审全过。没过的不许提交。

## 5. 验收 → 提交 → 发版

1. REQ §8 逐条填**实际命令 + 实际输出**，没跑过的不勾
2. `npm test` 全绿（全绿才算跑过）
3. `package.json` version = `CHANGELOG.md` 第一个 `## [x]` 标题（自检硬校验）
4. 提交按 `commit-convention` skill：一次一件事，标题 ≤50 字符，正文写「为什么」
5. 只 `git add` 本任务的文件，**禁止 `git add -A`**

**发版判据**：测试输出真实存在 + 版本两处一致。没有真实运行结果，就不要说「做完了」。

## 卡住的时候

- 连续三次没修好 → 停下质疑假设，不是继续试参数
- 被卡住直说，不要拿看起来合理的假结果糊过去
- 需求又模糊了 → 回第 1 步再问一次
