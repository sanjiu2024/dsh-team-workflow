# REQ-033 · 代码情报：把 MCP 里最值钱的两件事做成原生工具

- **状态**：已完成
- **对应版本**：`2.16.3 → 2.17.0`（加能力 → minor；同批还落了别人的 `2.17.1`）
- **提出**：YG，2026-10-31，原文：「帮我搜索一下，有没有对开发有利的skills和mcp或者dsh的插件，和省token的」→「那你帮我装到这个工作流里面，并且mcp不要用mcp形式进行调用」

---

## 1. 要做什么

把社区生态里对开发最有用、又能省 token 的两类能力**内化进本包**，以原生工具的形式注册（`ctx.tools.register`），
不引入任何 MCP 客户端、不引入第三方依赖、不发网络请求：

1. **仓库地图**（`repo_map`）—— 一次调用看清「这个仓库有什么、每个文件导出什么」。
   替代现在的「先 glob 一圈 → 再逐个 `read` 摸结构」。
2. **符号定位**（`symbol_refs`）—— 一次调用拿到某个符号的**全部定义与引用**（`文件:行` + 该行源码）。
   替代现在的「grep → 猜名字 → 再 grep 变体 → 逐个 read 确认」。

两条都只读、纯本地、零依赖。

## 2. 为什么（不做的后果）

模型每走一步都要把整份历史重发一次（见 `AGENTS.md`「上下文成本」：消耗 ≈ 地板 × 调用次数）。
现在探查代码库的标准路径是：`glob` → 读 3~5 个文件 → 发现不对 → 再 `grep` → 再 `read`。
一次「这个符号在哪、谁在调用」的问答常常吃掉 6~10 步，而每步都在重付整份地板。

社区里对应的正是 Serena（语义检索）与 repomix（仓库摘要）两个 MCP server —— 但 MCP 有两个代价：
① 工具 schema 常驻上下文（每 server 几百到几千 token）；② 需要 `mcp__server__tool` 的桥接形态。
本包既有形态（`lib/context7.js` 的 `docs`、`lib/lens-tools.js` 的 `lens_*`）已经证明：**直接注册原生工具更省、更可控**。

## 3. 不做什么

- **不接 MCP**：不加 `@deepseek-ai/dsh-mcp-client`，不注册 `mcp__*` 工具，不装社区 MCP 桥插件。
- **不做 LSP**：不起 `typescript-language-server` 之类的进程。符号识别是**正则级近似**，不是语义级 —— 这点必须在工具描述里写清，否则模型会拿它当编译器用。
- **不做工具渐进披露/工具表面裁剪**：改模型看到的工具集合会动请求前缀，缓存命中率可能被打穿；收益未实测前不动（候选见 §7）。
- **不装第三方 token 优化插件**（`dsh-token-optimizer` / `dsh-progressive-tools` 等）：本包 `rtk` + `magic-context` + `fold` 后端已覆盖同类机制，重复装等于把风险叠两层。
- **不做跨仓库索引 / 持久化索引**：每次调用现扫现算。索引文件一旦落盘就要处理失效，收益不成比例。

## 5. 已知约束（侦察出来的硬事实）

| 约束 | 证据 | 影响 |

| dsh 里没有 MCP 入口 | `lib/lens-tools.js:5` 注释（当初实测） | 「MCP 不用 MCP 形式」在架构上是自然的，不需要额外改造 |

## 6. 方案

新增 `lib/codeintel.js`（`CODEINTEL_DEFAULTS` / `CODEINTEL_FIELDS` / `installCodeintel` + 4 个纯函数），
配置出厂值 `team/extensions/codeintel.json`，在 `lib/index.js` 按现有 `layered()` 模式挂载，
并在插件返回值与加载日志里带上状态。

- 纯函数 `scanFiles` / `extractSymbols` / `buildRepoMap` / `findReferences` 单独导出，供自检直接验（不靠工具调用间接验）。
- 跳过表写死（`node_modules`、`.git`、`dist`、`build`、`target`、`vendor`、`.venv`、`__pycache__` 等），不做可配置的 ignore 语法 —— 现在没有这个需求。
- 体积上限三层：单文件字节上限（不读超大文件）、文件数上限、输出字符上限（超了截断并给收窄提示）。

不选「装 serena MCP」的理由：① 用户明确不要 MCP 形态；② 它要常驻一个 Python 进程 + 语言服务，装机成本与失败面都远大于一个纯函数工具；
③ 本包要装进别人的 profile，不能因为「省 token」反而把人家的启动搞坏。

## 7. 天花板（做完之后仍不支持的）

- 符号识别是正则近似：宏、装饰器生成的符号、同名重载、跨文件类型推断都看不见。
- 不认 `.d.ts` / 生成物（会被 `dist` 等跳过表挡掉，或因路径规则漏掉）。
- 不做语义检索（"哪个函数负责鉴权"这类要嵌入的事，本工具做不了）。
- 不做增量索引：大仓库（>2000 文件）每次调用都是全量扫，靠 `focus`/`path` 收窄。

| 严重度 | 问题 | 处置 |
| --- | --- | --- |

### 开发中修掉的两个真实缺陷

1. **地图列了函数内局部量**：第一版把 `const pkgRoot = …` 这类局部常量也当导出符号，本仓库真跑时 30 行里 22 个是噪音。
   → 改成只列模块级（缩进的 `function`/`const` 不进地图），地图与定位的口径差异写进注释。
2. **常量挤掉函数**：`maxSymbolsPerFile=10` 时，`tools/mc-call.mjs` 只列了 10 个顶层 `const`，5 个函数全看不见。
   → 同文件内按 `fn/class/type → method → const` 排序后再截断。
