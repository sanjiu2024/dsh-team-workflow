# REQ-012 · 审查改成两层：std 测，power 判（power 不带工具）

- **状态**：已完成
- **对应版本**：`1.16.0 → 1.17.0`（改团队默认行为 → minor）
- **提出**：用户，2026-10-08，原话：「把审查改为，那种重大变化或者写完一个大部分才能使用 power
  进行审查，并且 power 审查不带任何工具，只凭自己的感觉，测试则让 std 测」

---

## 1. 要做什么

把团队规范里的审查从「三层」（1 正确性 `tier-std` / 2 整体性 `tier-power` / 3 安全破坏性
`tier-power`）改成两层，**按产物分工**：

- **std 测**（`subagent_std`，**带工具**）：跑测试、跑反向实验、逐条核实、`grep` 调用方。
  **每完成一块就跑** —— 它是那个「便宜到每个增量都跑得起」的一边。
- **power 判**（`subagent_power`，**一个工具都没有**）：只凭主 agent **贴进 prompt** 的材料
  挑毛病。**只在重大变化或写完一个大部分时派。**

「不带任何工具」要**在配置层强制**，不能只写在提示词里 —— 用户要的是「只凭自己的感觉」，
不是「答应我别用工具」。

## 2. 为什么（不做的后果）

原来的三层都能自己读文件、自己跑命令：它们会顺着仓库扫到超时（上游 42 次 reviewer 实测，
最慢一次 108 轮、80 次 `grep` + 72 次 `read`，跑满 30 分钟被超时砍掉，97-100% 的时间耗在
模型生成上）。而且两层 `power` 干的是同一件事（读代码挑毛病），叠层数没有换来新视角 ——
换视角靠的是**分工**。

不做的话：每次审查都可能跑成几十上百轮，且审查结论与「跑过什么」混在一起，说不清哪些是
验证过的、哪些只是判断。

## 3. 不做什么

- **不取消增量审查**：std 测仍然每完成一块跑。这次只把**贵的那一边**（power 判）挪到
  「重大变化 / 写完一个大部分」。
- **不删「派审查必须给边界」**（上游 pi-workflow v1.13.5 移植的那条纪律）：原话保留，
  `scripts/selftest.mjs` 的断言也不动。
- **不给 power 加回任何工具**，哪怕是只读的 `read` —— 能读文件就会自己探索，这正是要断掉的。
- **不改 `tier-max`**：它仍带工具（质疑方案要能自己看），也不受 `toolLessTiers` 影响。
- **不改其它档位的模型/网关**，只加一个「剥工具」的开关。

## 5. 已知约束（查出来的硬事实）

| 约束 | 证据 | 影响 |
| --- | --- | --- |
| `toolFilter` 是 `tool-subagent` 的**配置字段**，形状 `{ allow?: string[], deny?: string[] }`；过滤掉的工具「从子代理提示里消失 + 调用被拒」，未知工具名会让**启动失败** | `dsh-tool-subagent/lib/types/index.d.ts:53-63` | 能表达「一个工具都不给」，且 `allow: []` 没有名字要校验 |
| 空 `allow` 就是全禁（不是「没给过滤」） | `dsh-tools/lib/index.js:2642` `admits()`：`filter.allow !== void 0 && !filter.allow.has(name)` → 空 Set 对每个名字都返回 false | `allow: []` 语义正确，不会被当成 falsy 短路 |
| 这条能力由 **spawn in-process** 提供，否则 mount 期就抛 `does not support the "toolFilter" capability` | `dsh-subagent/lib/index.js:3196`；能力表在 `dsh-subagent-spawn-in-process`（`toolFilter: true`）；`dsh-subagent/lib/index.js:522` 执行 `ctx.tools.restrict(composition.toolFilter)` | 我们那条工具行的 `provider: spawn` 正好对得上 |
| 团队预设是 `preset install` 从**当前出厂** `standard.patch.yml` 现改出来的产物 | `bin/dsh-team.mjs:630` `findRc2StandardPatch()` | 新增键必须走 `lib/preset-gen.js`，不能手改落盘预设（下次重生成就覆盖） |
| dsh 的子代理**没有角色概念**，档位钉在工具行上 | `team/agent-settings.json` 的 `_subagents 为什么要改` | 「审查档」只能靠给某一条工具行加 `toolFilter` 表达 |

## 6. 方案

1. `team/agent-settings.json` 新增 `subagents.toolLessTiers: ["power"]`（列在里面的档位生成
   `toolFilter: { allow: [] }`）。
2. `lib/preset-gen.js` 的档位工具行生成器：`toolLess.includes(tier)` 时多插两行
   `toolFilter:` / `allow: []`（插在 `agentOptions` 之前）。
3. `team/RULES.md`：审查节整体重写 —— 分工表、std 测什么、power 怎么判（含「材料全靠你贴」
   的代价与「结论是判断不是验证」）、两份派单模板、什么时候派、修复与轮次、略过、成本提醒；
   选档表与角色声明表同步。
4. `skills/workflow/SKILL.md` 第 4 节、`README.md` 两处、`docs/UPSTREAM-SYNC.md` 两处
   （旧理由引的是已废的三层策略，加【2026-10-08 后续】说明结论不变）同步。
5. 自检：`scripts/selftest-preset-gen.mjs` 新增断言（夹具一次 + **真配置一次**），
   `scripts/selftest.mjs` 的 workflow 关口名跟着改。

为什么不选别的路：

- **只写提示词「别用工具」**：那不是强制，模型想读还是会读 —— 用户要的是「只凭自己的感觉」。
- **用 `deny` 列出所有工具名**：工具名会随 dsh 版本变，`allow: []` 不需要维护名单。
- **保留三层但把第 2/3 层降档**：没解决「审查者自己探索到超时」这个根因。

## 7. 天花板（做完之后仍不支持的）

- **power 判看不到代码**：材料全靠主 agent 贴，贴漏了它就判不到 —— 这是这套设计的**固有代价**，
  不是 bug。它的结论必须由主 agent 用工具核实后再动手。
- **`toolFilter` 只在配置层对「子代理工具行」生效**：主 agent 自己、`tier-max`、squad 成员
  都不受影响（成员的工具面由 `team/extensions/squad.json` 的 `bash` 开关管）。
- **要重启 dsh 才生效**（预设是加载期挂载的）。本次**没在真 dsh 进程里端到端验证**「power 真的
  没有工具」，只有源码级证据（见 §5 与 §8 的独立验证）。端到端为什么做不了，有两条具体原因：
  ① 本会话的子代理深度是 1 / `maxDepth 1`，再派一层直接报
  `Error: subagent depth 2 exceeds maxDepth 1`；② 正在跑的那个 dsh 进程启动于预设重生成**之前**，
  它挂的是旧预设。
- 历史文档与代码注释里仍留着「第 N 层审查指出」这类**过去时的归属**（`lib/computer.js:645`、
  `lib/mc-config.js:328`、`lib/squad-tools.js:38`、`bin/dsh-team.mjs:880`、`lib/worktree.js:9`）——
  它们记的是当时那轮审查，不改。

### 独立 std 测报回的两条 P2（**略过**，记录在案）

- `P2 · dsh-tools/lib/index.js:2979 · 非 native 模式下会无条件把 run_code 塞回 visible` ·
  **略过**：本部署默认 native（`:2670`/`:2705`），`standard.patch.yml` 与已装预设都没有 `mode:`，
  所以不成立。将来谁给 agent 设了 `ptc`，power 会重新看到 `run_code`（它内部能调的工具同样被过滤）。
- `P2 · dsh-tools/lib/index.js:2979-2984 · restrict 只过滤「继承」的工具，agent 自己层注册的不过滤` ·
  **略过**：power 那条行没传 `outputSchema`，子代理自己层不注册任何工具
  （`dsh-subagent-in-process-driver/lib/index.js:55` 仅在有 schema 时注册），当前不成立。

两条都是「换个部署配置才成立」的未来风险，不影响本次交付；记在这里是为了下次改 `mode:` 或给
档位加 `outputSchema` 时能想起来。
