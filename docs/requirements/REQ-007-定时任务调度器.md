## 1. 要做什么

原话（用户）：

> 「这个是 tauri 框架 deepseek harness desktop 的桌面版的内置插件，你帮我移植到我这个工作流里面，并为扩展」
>
> 追认范围时选：「host + client 面板（需要先给本包搭 client-plugin 基础设施）」
>
> 追认「为扩展」时自填：「在安装这个工作流为可选安装这个」

翻译成两件事：

1. **移植**：把 `dsh-tauri-scheduler` 的能力搬进 `dsh-team-workflow`，成为本包的一个模块，和 `worktree` / `computer` / `bash-linux` 平级。
   能力 = 建定时任务（8 种计划）→ 到点在**全新会话**里无人值守跑一段 prompt → 记运行历史 → 出结果/失败都能查。
   宿主侧给 4 个 agent 工具 + 一组 HTTP 路由；客户端给 dsh Web GUI 一个面板。
2. **扩展 = 可选安装**：整块能力**默认关闭**。装了工作流不等于装了调度器；要开的人自己开。
   默认关闭必须是真的关（路由 404、工具不注册、面板不出现），不是「关掉了但还占着位置」。

## 2. 为什么（不做的后果）

- 桌面版那套插件装在 Tauri 桌面 profile 里，本机跑的是 npm 版 dsh（`web` profile），**用不上**。
- 团队工作流目前**完全没有定时/周期任务能力**（全仓 grep `cron` / `scheduler` 零命中，见 §5）。
  意味着「每天早上跑一遍审查」「每 15 分钟盯一次构建」这类事只能靠人记得。
- 官方 `@deepseek-ai/dsh-schedule` 不能替代：它把提醒作为 follow-up **投递回原会话**，
  而这里要的是**起一个全新会话无人值守跑完**（见 §5 的语义对比表）。

## 3. 不做什么

| 不做 | 为什么 |
| --- | --- |
| 不移植 `timeZone` 任务字段 | 源头是**死字段**：`schedule.test.ts:4` 自承 cron-schedule 无 tz 支持，按进程本地时区算。搬一个不生效的字段比不搬更坏 |
| 不做 model picker / prefill bridge / session icons / recommendations | 桌面版这四块（`components/model-picker.tsx` 195 行、`prefill-bridge.*`、`register/session-icons.ts` 90 行、`recommendations.*` 121 行）服务的是桌面客户端的会话输入框集成，本包没有那套壳。模型选择退化为「留空 = 跟随默认模型」 |
| 不做 Tailwind / `cssr` 样式系统 | 本包零依赖。客户端面板手写内联样式 |
| 不做 i18n | 本包其余模块全是中文单语。面板中文 |
| 不做「错过补偿队列」 | 保持原语义：`nextRunAt` 已过就立即跑一次，错过多个周期只补跑一次（`scheduler.ts:63-70`） |
| 不引 `cron-schedule` / `lodash-es` / `pathe` | 本包零依赖。daily/workdays/weekly/monthly 直接算下一个本地钟表时点，比源头「拼 cron 表达式再解析回来」更直白 |
| 修源头的 `custom` bug | 源头校验了 `time` 却从不使用它（`anchoredOccurrence` 只按 anchor + N×天 算），于是「每 3 天的 09:00」实际用的是 anchor 自带的时刻。这里让 `time` 真正生效，自检里钉了回归测试 |
| 不改动官方 `@deepseek-ai/dsh-schedule` | 它是另一套语义（投递回原会话），两者可以并存。本模块不碰它，也不抢占 `schedule_*` 工具名 |
| 不做 headless / sdk profile 适配 | `webServer` 服务只在 web profile 有（`dsh-web-app/cordis.patch.yml:169-170`）。没有 `webServer` 时本模块自降级为「只有工具、没有面板」，不报错 |
| 不做跨进程锁 | 写队列只在进程内串行。多开 dsh 共用 `DSH_HOME` 时是「后写覆盖先写」——已用 pid 把 `recoverInterruptedRuns` 的误伤挡住了，但没有真正的文件锁（见 §7） |
| 不自动提交、不自动推送 | 团队基线 |

### 6.2 宿主侧设计

**存储**：`<DSH_HOME>/team-workflow/scheduler/{tasks.json,runs.json}`，`{version:1,...}`。
写走一条全局串行队列（`createStore` 内部的 `serialize()` Promise 链）+ 临时文件 + `rename` 原子替换。
运行历史保留最近 200 条。

**计划计算**：手写 `nextOccurrence(schedule, from)`，8 种：

```text
once      下一个 at（必须严格未来）
hourly    下个整点的 :minute
interval  everyMinutes 固定步长；有 anchor 就从 anchor 对齐，没有就从 now 起
custom    每 everyDays 天的 time（需要 anchor）
daily     每天 time
workdays  周一~周五 time
weekly    指定星期集合 time
monthly   每月 day 号 time
```text

后四种**不转 cron、不引库**，直接算下一个本地钟表时点（比源头更直白：源头为了用 `cron-schedule` 绕了一圈表达式）。

`interval` / `custom` 的锚点语义：有 `anchor` 时对齐到「从锚点起 N 步」的网格上、且**严格大于 `from`**
的下一个刻度（`Math.floor((from - base) / step) + 1`）；没有 `anchor` 就从 `from` 起算。

**调度循环**：`setInterval(tickMs)`，默认 1000ms。
一次 tick：读全量 → 补算缺失的 `nextRunAt` 并落盘 → 取到期的且不在 `running` 集合里的
→ 按剩余并发额度启动。全局并发上限 4，同一任务不并发。
`unref()` 掉定时器，别拖住进程退出。

**`nextRunAt` 在「启动的那一刻」就推进**（不是在 finally 里）—— 否则一次跑 20 分钟的任务，
在这 20 分钟里每个 tick 都会被判定为「到期待跑」，靠 `running` 集合去挡是脆的（进程重启就丢）。
启动即推进 + `running` 集合 = 双保险。

`once` 任务触发后写 `enabled=false` + `nextRunAt=null`，不会重复触发。

**执行器**：照抄桌面版 `executor.ts` 的骨架，但**简化了一处**——
`sessionId = task-<runId>` → `agents.withoutInitiator(() => agents.create(...))`
→ `setup` 里 `agentPresets.mount` + `setApprovalPolicy(session, "never")`（**不装 model selection**：
`agentOptions` 直接传给 `agents.create`，省掉一次 `ctx.loader` 依赖）
→ `await agent.whenIdle()` → 钉标题 + `workspace.attachSession`
→ `followup(createUserMessage({content:[{type:'text',text:prompt}], source:{kind:'scheduler',...}}))`
→ 等 idle（`runTimeoutMinutes` 上限，超时 `cancel`，`cancelTimeoutMs` 不收敛记 `cancel_convergence_timeout`）
→ 全量快照 → `sessions.flush` → 摘要 → 判定成功/失败。

**摘要用全量快照（`session.snapshotEvents()`），不用增量流。** 源头是「先增量收、缺 `turn/end`
再回退全量」（`docs/sync-log.md:257-262` 特意与上游不同）；这里会话是**全新的**，
所有事件都属于本次运行，所以直接走全量 —— 一条路，且天然是那个更安全的回退路径。
**「缺 `turn/end` 判成功」**（这条初稿时写反了，实现时纠正）：核心在异常收尾（取消 /
中断 / 崩溃修复）时可能就是不补写这条事件，而这里读的是**全量快照** —— 拿它判失败
是在制造假失败。代价是「跑一半断了」和干净收尾同形，所以判定从宽、**证据不能丢**：
这一轮记 `succeeded` + `incomplete: true`，并且
- 一个事件都没有时另记 `noEvents`（与「有事件但没收尾」分开：前者连「跑过没有」都
  说不出来，可能是会话结构漂移、观测不到）；
- `scheduler_list` 和面板都把结论说出来（失败 / 成功 / 收尾不完整），不能只报时间戳。

**4 个工具**（名字沿用源头，避免与官方 `schedule_*` 撞）：

| 工具 | 入参 | 返回 |
| --- | --- | --- |
| `scheduler_create` | `name`,`prompt`,`schedule` 必填；`workspaceId`,`permission`,`provider`,`model`,`reasoningEffort` 选填 | `{ok,taskId,nextRunAt\|null,error?}` |
| `scheduler_list` | 无 | `{report}` —— 模型看到的是 `output.render` 出的那份中文报告（名称/计划/下次运行/状态），不是原始 JSON |
| `scheduler_update` | `task_id` 必填；其余选填；`run_now` 立刻触发一次 | 见下面那张表 |
| `scheduler_delete` | `task_id` | `{ok,error?}` |

`scheduler_update` 的返回分三种情形（判别靠 `updated` / `ran` 是否存在）：

| 情形 | 返回 | render |
| --- | --- | --- |
| 只改字段 | `{ok:true,taskId,updated:true,nextRunAt}` | ✅ 已更新 |
| 只 `run_now`，触发成功 | `{ok:true,taskId,updated:false,ran:true,nextRunAt:null}` | ✅ 已触发 |
| 改字段 + `run_now`，触发成功 | `{ok:true,taskId,updated:true,ran:true,nextRunAt:null}` | ✅ 已更新并立刻触发 |
| 补丁已存但触发失败 | `{ok:true,taskId,updated,runError}` | ⚠️ 已保存改动，但立刻运行没起来…（**不用重试**） |
| 补丁本身被拒 | `{ok:false,error}` | ❌ 更新失败 |

两处刻意做成这样：

- **触发失败不再回 `ok:false`**。`ok:false` 的含义是「这次调用没生效」，而补丁是落了盘
  的；报成失败会让调用方重试补丁（重复改）或以为改动没落地。所以拆出单独的 `runError`。
- **`run_now` 成功路径回 `nextRunAt: null`**。手动触发跑起来会走 `advance` 重算下一次，
  而 `trigger` 只是 `fireAndForget` —— 返回时后台那一轮还没走到 `advance`，此刻存里那个
  是**马上要变**的值。「触发后重读存储」也修不了：`execute` 的第一个 `await` 就在
  `advance` 之前，同步读到的必然是旧值。没有一个正确的数可报，就不报，render 里指明去
  `scheduler_list` 查当下真值。

**HTTP 路由**：前缀 `/api/team/scheduler`（本包自己的命名空间，不用桌面版的 `/api/desktop/...`）。

```text
GET    /api/team/scheduler/tasks          列表（支持 ?search=）
POST   /api/team/scheduler/tasks          新建
PUT    /api/team/scheduler/tasks          更新
DELETE /api/team/scheduler/tasks          删除（body {id}）
POST   /api/team/scheduler/tasks/toggle   启停
POST   /api/team/scheduler/tasks/run      立刻跑一次
GET    /api/team/scheduler/history        运行历史（?taskId=）
DELETE /api/team/scheduler/history        删一条历史
GET    /api/team/scheduler/options        工作区/权限/模型目录 + 默认模型

校验先于落盘；缺 id / 非法体一律 400 + 中文 error。

### 6.4 可选安装怎么落

三层，缺一不可：

1. **默认关**：`team/extensions/scheduler.json` 的 `enabled: false`。
2. **行为上真关**：`installScheduler` 在 `enabled !== true` 时**立刻返回**，一个工具不注册、一条路由不挂。客户端靠探活失败不注册面板。
3. **开/关有人管**：`dsh-team scheduler enable|disable|status` 改那个 JSON 并提示重启。

选这条路而不是「拆成第二个包」：拆包要多维护一个 `files`/`version`/`cordis.patch.yml`，
而本包已有 `dsh-team preset install` 生成同伴包的先例，但那套是给 profile 级 bundle 用的，
调度器不需要新 bundle 行 —— 它已经是本包的一部分，只需要一个开关。
（若将来确实想让「没开的人连客户端 bundle 都不下载」，再拆包，见 §7。）

### 6.5 装配进 `lib/index.js`

**`lib/index.js` 的顶层 `inject` 一个都不加。** 全部依赖由模块内部的 `ctx.inject` 声明：

```js
// lib/scheduler.js
export function installScheduler(ctx, { config }) {
  if (config?.enabled !== true) return { enabled: false, ... };   // 关着：零注册
  return ctx.inject(SCHEDULER_DEPS, (scope) => { ... });          // 依赖齐才装配
}
```

原方案打算把 `agents` 等加进顶层 `inject`，只把 `webServer` 拿出来条件挂载。**改成全都不加**，
理由是同一个失败模式比预想的宽：

> `inject` 里出现但当前 profile 没有的服务，会让**整个插件**静默不激活 ——
> cordis 的 `_checkImpl`（`cordis/lib/index.js:1306-1315`）检查的是「声明的依赖是否全部可解析」，
> 不区分「谁需要它」。

也就是说，只要有一个 profile 没有 `agentPresets`（或将来 dsh 改了服务名），
**团队基线、审计日志、linux 命令会一起消失**，而且没有任何报错。
这个代价远大于「调度器少挂一条路由」。所以调度器的依赖**一个都不进顶层 `inject`**：
依赖不齐时只有调度器不激活，本包其余模块毫发无伤。

需要的是：`agents`, `agentPresets`, `agentDefaultModel`, `sessions`, `workspaceRegistry`
（+ 条件挂路由用的 `webServer`）。**不需要** `permissionPresets` / `llm` / `connection`
—— 审批走 `setApprovalPolicy(session, "never")`，模型走 `agents.create({agentOptions})`，
都不用额外服务。

### 6.6 无人值守的安全边界（第 1/3 层审查后加硬的部分）

这个模块和本包其它模块有一个本质区别：**它会在没人看着的时候自己起会话、自己调工具。**
所以下面这些不是「顺手加的防御」，是这个功能能存在的前提。

**① 沙箱档位是唯一的安全边界，而且必须钉住。**

审批策略被强制设成 `never`（没人能点「同意」，否则工具调用会永远卡着），
所以「这个任务能写什么」全靠 `permission` 一项。做法：

```js
setup(agentCtx, agent) {
  agentCtx.tools.restrict({ deny: SCHEDULER_SELF_TOOLS });  // 禁自我繁殖
  setSandboxMode(agent.session, task.permission);           // @deepseek-ai/dsh-sandbox-policy
  // 回读核对：会话日志里那条 sandbox/mode 事件（拿不到再试 ctx.sandboxPolicy）
  if (readPinnedMode(agent) !== task.permission) throw new Error("档位没钉上");
  pinned = true;
  setApprovalPolicy(agent.session, "never");                // @deepseek-ai/dsh-user-approval
}
```

顺序不能反（两者都写会话投影）。任一失败 → 记住 `setupError` 并抛出，
`agents.create` 之后立刻 `dispose` 掉那个 handle、本轮记成 failed ——
**绝不在沙箱没设上的情况下把 prompt 发出去**。

> 为什么不用 `permissionPresets.set(session, name)`：本机那份预设表
> （`dsh-permission-presets/lib/index.js:143-156`）只有 `workspace-write` 和
> `danger-full-access`，**没有 `read-only`**，而且传未知名字直接抛。直接调
> `setSandboxMode` 才是稳的（`lib/types/session-mode.d.ts:49`）。

**② 禁止自我繁殖（这条是提权路径）。**

`scheduler_*` 是**全局**工具，无人值守会话一样看得见。不禁掉的话：

> 一个 `read-only` 的任务 → 调 `scheduler_create` → 建一个
> `permission: "danger-full-access"` 的新任务 → 下一跳就以全权限跑起来。

所以 `setup` 里 `agentCtx.tools.restrict({ deny: ["scheduler_create","scheduler_update","scheduler_delete"] })`
（`dsh-tools` 的 `ToolRestriction`，`lib/types/index.d.ts:644`）。
留 `scheduler_list`：只读，模型看一眼「还有什么在排」是有用的。

**③ 路由要自己的栅栏 —— dsh 的 web server 不鉴权。**

`dsh-host-webserver` 直接 `listen`，全包没有 Authorization / CSRF。挂上去的路由默认对
「本机任何进程 + 用户浏览器里的任何页面」都是开的。不设栅栏的话：

- 恶意网页用 `fetch(url, {mode:'no-cors', headers:{'content-type':'text/plain'}, body:...})`
  就能 POST 建任务 —— `text/plain` 不触发预检，body 照样解析成 JSON；
- DNS rebinding 把域名指到 `127.0.0.1`，就能**读走**全部任务的 prompt 与运行历史。

`isTrustedRequest()` 四条判据（照抄本机同 profile 的第三方插件
`@linxin666/dsh-client-ui-git-graph/lib/index.js:1315-1333`）：socket `remoteAddress` 是回环
（权威，不看 `X-Forwarded-For`）、`Host` 头也是回环（挡 rebinding）、
`sec-fetch-site !== "cross-site"`、有 `Origin` 时必须与 `Host` 同源。
**栅栏在 handler 最前面，`/options` 探活也拦** —— 客户端拿到 403 照样不注册面板，
行为与「没启用」一致。

**④ 任务数上限在写队列里把关。**

每个任务到点都起一个真会话，无上限 = 无界建会话。`insertTask()` 把
「读长度 → 判断 → push」全放进**同一个** `mutateTasks` 回调：
先读再判再写的话，两个并发请求会同时通过检查。

**⑤ 存储坏了不许静默清库。**

`readFile(..., {strict:true})` 是写路径用的：文件不是合法 JSON 就**抛**，
抛之前先把坏文件改名成 `<file>.corrupt-<ts>` 留证。读路径保持降级（面板还打得开）。
原来的「解析失败返回 `[]`」→ 下一次写入把它整体覆写成空数组 = 用户的任务全没了、
没有任何痕迹。

**⑥ 权限天花板 —— 栅栏挡不住的那一半。**

第 3 层复审指出：上面 ③ 的 `tools.restrict` **不是能力边界**。一个已经在跑的无人值守
会话手里有 bash，它可以 `curl` 打本机 `/api/team/scheduler/tasks` —— 回环 socket、回环
`Host`、无 `Origin`、无 `sec-fetch-site`，四条栅栏全过 —— 自己建一个
`permission: "danger-full-access"` 的任务。`restrict` 只约束本会话的工具表，
管不到子代理，更管不到 shell 里的 `curl`。

所以真正的边界必须在**服务端**：`maxPermission`（默认 `workspace-write`）是任务级
`permission` 的天花板，`insertTask()`（覆盖 HTTP 与工具两条建法）和两条 update 路径
（`scheduler_update` 与 `PUT /tasks`）都过 `checkPermissionCeiling()`。想放开到
`danger-full-access` 得自己改 `team/extensions/scheduler.json` —— 那是一次有意识的
操作，不是模型能顺手做的。`GET /options` 也只列到天花板为止：面板上不该出现一个
选了必然被拒的档位。

**⑦ 放行判据必须是正向的。** `setup` 里任何一步失败都算失败 —— 但「没记下 `setupError`」
本身**不是**「沙箱钉上了」的证据：宿主漂移让 `agents.create` 根本不调 `setup`
（选项改名、被自己的包装吃掉）时，`setupError` 也还是 `undefined`。所以放行判据改成
**写进去再读回来**：沙箱写完回读会话日志里那条 `sandbox/mode` 事件、审批写完回读那条
`approval/policy` 事件，两者都对上了才置 `pinned = true`，`!pinned` 一律 dispose + failed。

**两条边界都要回读，不能只回读沙箱。** 审批静默失效同样致命，只是死法不同：沙箱没钉上
是**越权**，审批没设成 `never` 是工具调用**永远卡着**等人点 —— 而调度任务是无人值守的，
没有人会来点。

读法对着源码核过（`session.append` 是同步的，所以 setter 返回时事件必然已在日志里）：
`setSandboxMode` → `session.append("sandbox/mode", { mode })`
（`dsh-sandbox-policy/lib/index.js:41`）；`setApprovalPolicy` →
`session.append("approval/policy", { policy })`（`dsh-user-approval/lib/index.js:63-65`）。
沙箱那条还留了第二路 `ctx.sandboxPolicy.overrideOf(session)` 作保险（它不在
`REQUIRED_SERVICES` 里，拿不到就算了）。

**⑦b 一次更正：`setup` 抛异常是会 propagate 的。**

初版文档在这里写过一句「`agents.create` 不保证透传 `setup` 的异常」。**那句是错的**，
对着源码核过：`dsh-agent-loop/lib/index.js:1889` 是
`(await raceAbort(setup?.(prepared.agent.ctx, prepared.agent), …))?.commit()` ——
`setup` 被 `await`，异常经 `initializeAgent` 的 catch（那里会 `prepared.dispose()`）
再由 `setupAndPublish` 重抛，`create()` 因此 reject。所以
`agentCtx.tools.restrict()` 当初落在 try 外面**确实**会让失败文案不准（走的是
「创建会话失败」而不是「准备无人值守会话失败」），但**不会**造成「在没钉沙箱的会话里
发 prompt」—— 那种情况下 `create` 自己就拒了。

顺带核掉了另外两个假设（原先都只是假设）：`setup` 的第二个参数就是 `handle.agent`
（同一对象，`setup?.(prepared.agent.ctx, prepared.agent)`），且我们传的 `setup` 是同步
函数、返回 `undefined`，`:1889` 那个 `?.commit()` 对它是空操作。

**真正要防的是另外两种形态**，它们才是这一段的存在理由：

- setter **不抛却不生效**（宿主静默漂移）
- `setup` **压根没被调用**（选项改名 / 被上层包装吃掉）

这两种下 `setupError` 都是 `undefined`、`create` 也正常返回 —— 只有正向回读拦得住。
三步仍在同一个 try 里（文案准确性 + 有异常时优先报它），但放行判据是 `pinned`。

**⑧ 执行时再查一次天花板。** 只在写口拦 = 只拦新增不拦存量。调低 `maxPermission`
之后，库里那些旧任务、手工改过的 `tasks.json`、旧版本留下的记录，都还能靠 `run_now` /
`toggle` / 定时触发重新跑起来。`run()` 开头会再查一遍，超了直接 failed 且**连会话都不建**。

**⑧b 一条必须说清的残余提权链：`read-only` → `workspace-write`。**

`read-only` 在 dsh 里管的是**文件写入**（`writableRoots()` 在 read-only 下返回空数组，
`dsh-sandbox/lib/index.js:159-164`），它**不拦 exec**。所以一个 `permission: "read-only"`
的无人值守会话手里仍有 bash，它能 `curl` 本机 `/api/team/scheduler/tasks` ——
回环 socket + 回环 Host、无 Origin、无 sec-fetch-site，四条栅栏全过 ——
自己建一个 `permission: "workspace-write"` 的任务，那个任务就能写文件了。

这条链**没有被任何一条加固覆盖**，也不假装覆盖：

- `tools.restrict()` 只管本会话的工具表，管不到 shell 里的 `curl`
- 工具名（`scheduler_*`）拦不住 HTTP 路由
- `maxPermission` 只能钉住链的**终点**，钉不住「能不能走这一跳」

所以真正的对策是**选对 `maxPermission`**：把它设成 `"read-only"`，这条链当场断掉
（任何路径都不许建出比 read-only 高的任务）。默认给 `workspace-write` 是更实用的取舍，
这是一个**有意识的选择**，不是疏漏。

**⑨ 手动触发也要受并发上限约束。** `trigger()` 原来只查「这个任务在不在跑」，
不看 `running.size`。`POST /tasks/run` 和 `scheduler_update` 的 `run_now` 都走它 ——
`maxTasks` 默认 200，也就是能同时起 200 个真会话。

另外几条不那么致命但同样修了的：`readJsonBody` 挂 `close`/`aborted`（否则客户端断连时
promise 永不 settle，每断一次漏一个 handler）；handler 的兜底 catch 只在
`BadRequest` 时回 400，其它内部故障回 **500**（全回 400 会让「存储坏了」看起来像
「你参数填错了」）；超限时不再 `req.destroy()`（socket 一没，那个 400 到不了客户端，
客户端只看到 `ECONNRESET`），改成排空 + `settled` 标志；
`recoverInterruptedRuns` 加时间兜底（pid 会被系统复用，另一个 dsh 崩在任务里、
它的 pid 后来分给别人，`isProcessAlive` 就永远 true，那条记录永远留在 `running`）；
`validateSchedule` 之外补了 `explainScheduleProblem()`，让面板上清空「第几分」时
报的是「hourly 需要 minute（0-59 的整数）」而不是一句笼统的「schedule 不合法」；
`dsh-team scheduler enable/disable` 写配置改成临时文件 + `rename`。

## 7. 天花板（做完之后仍不支持的）

- **计划不认时区**：与原实现一致，一律按宿主进程本地时区算。跨时区协作的人会看到偏移。
- **不做分布式**：多开 dsh 进程会各跑各的，同一任务可能被跑两遍。没有跨进程文件锁
  （写队列只在进程内串行）。已做的补偿：运行记录带 `pid`，`recoverInterruptedRuns`
  只动本进程或已死进程留下的 `running` 记录，不会把另一个 dsh 正在跑的那一轮标成中断。
- **运行历史裁剪只裁 `runs.json`，不删会话**：`historyLimit` 到了会丢掉旧的运行记录，
  但那些会话是用户自己的数据，本模块不碰（删会话是不可逆操作，不该由一个「清理历史」
  的动作顺手做掉）。
- **不做错过补偿队列**：停机三天，`interval` 任务只补跑一次，不是三次。
- **不做重试**：一次失败就是失败，等下一个周期。没有退避策略。
- **客户端面板是子集**：没有模型选择器、没有推荐方案、没有会话输入框集成、没有 i18n、没有拖拽排序。
- **面板只在 web profile 出现**：headless / sdk profile 下只有 4 个工具，没有 UI。
- **`dsh-team scheduler` 只能改配置文件**：改完要重启 dsh 才生效（本包没有热重载钩子）。
- **`permissionRank` 对「缺失/未知 `permission`」按最严处理**：手改过的旧任务会被拒，
  文案显示「权限档位「undefined」」。改成「按默认档位计」会让**没有权限字段的任务反而
  通过天花板检查** —— 用一个宽松判断换掉保守判断，方向不对。保持现状。
- **`run_now` / `/tasks/run` 没有鉴权与限速**：任何带 bash 的会话（含 `read-only`）都能
  循环 curl 触发「在天花板以内」的任务，烧额度并占满并发把定时任务饿死。这是「起会话」
  这个能力本身的下界（同一个会话本来就能直接起子会话），不是本插件引入的；
  对策是 `maxPermission: "read-only"`（§6.6）。
- **客户端 bundle 无论如何都会被打包分发**：`dsh.client` 是 package.json 级声明，关不掉。
  真要做到「没开就不下载」，得把客户端拆成第二个包（本次不做）。

1. **假失败和假成功都源自「拿观测不到的信号下结论」。** 第 2、10 条的修法是同一个不变式：

   默认 `true`。反过来第 6 条：判成功可以宽松，但**证据必须留下**（`incomplete` 标记）。
2. **写负向验证时前提搞错，测试就是摆设。** 第 15 条的测试我第一版把「停用」放在

   `now + 10min`，正好等于 `plan` 自己会算出的值，新旧代码都是绿的；改成

**没修、也不打算修的**（不是漏，是有意的）：

- `read-only` 的无人值守会话带 bash 时，仍可以 `curl` 回环自建一个 `workspace-write`
  任务（四条信任栅栏全部通过）。对策是 `maxPermission: "read-only"`，写在 6.6。
  这是**已知边界**，不是待办。
- 第 10 条那个 30 秒的启动窗口落在 `runTimeoutMinutes`（默认 30 分钟）之外，单次运行
  最坏时长因此是「30 分钟 + 30 秒」。有界，不修（上限见 §12）。

### 12. 三档审查后的第 2 轮修复（2026-10-06）

§11 那轮修完之后又跑了一遍三档审查（第 1 层正确性 / 第 2 层整体性 / 第 3 层安全），
这轮的结果。**一条缺陷一个提交**，共 8 个：

| # | 缺陷 | 危害 | 提交 |
| --- | --- | --- | --- |
| 1 | `nextRunAt` 的 schema 声明成 `string`，实际一直返回数字 | dsh 会拿 `output.schema` 校验工具返回值，不符就**抛异常** ⇒ 每一次成功的 `scheduler_create` 都在工具边界失败 | `e839998` |
| 2 | `waitForTurnStart` 那个块用 `check(` 包 `async` 回调 | `check` 是同步包装器，promise 没人接 ⇒ **第一个 `await` 之后的断言从来没跑**，自检却报全绿、退出码 0 | `6550339` |
| 3 | 手动触发会吃掉**将来那一格** | 还没到的一次性任务被手动跑一次就 `enabled=false` + `nextRunAt=null`，下次再也不触发；无锚点 `interval` 被顺延一整个周期。而工具回 ✅ | `98ac5ff` |
| 4 | `trigger()` 不查权限天花板 | 回 `{ok:true}`/HTTP 200「已触发」，实际一个会话都没起 —— 权限拒绝被成功文案盖住，只剩事后一条 failed 记录 | `06ebaa9` |
| 5 | `scheduler_list` 看不出「上次跑成什么样」 | 运行结果只进 `/history` 和面板，而**没有 history 工具** ⇒ agent 侧唯一的读路径只有时间戳 | `e413af5` |
| 6 | 「一个事件都没有」和「跑了但没收尾」分不开 | 两种形状都留一条空摘要。判定都从宽（零事件判失败就是假失败），但证据要分得开 | `59f149d` |
| 7 | `updated:false` 的 `runError` 文案自相矛盾 | 「什么都没改」+「改动已生效，**不用重试**」——而这是调用方判断要不要重试的唯一依据 | `31e2a6c` |

第 8 条（`turnStartTimeoutMs` 配成 `NaN`/超大值时这一轮**永不返回**）单列在 `7d23659`：
包内那份配置过 `SCHEDULER_FIELDS`，但插件配置那一路是 `layered()` 的 `...override`
**原样展开**、不过 FIELDS —— 结构上拿不到「值一定合法」的保证。收口成纯函数
`normalizeTurnStartTimeout`（不可信 → 默认 30s；可信 → 夹到 `[50ms, 5min]`），
两处调用都用它。上限是新加的：这个等待在 `runTimeoutMs` 的 race **之前**，没上限就
等于「一轮最坏时长无界」。

**这轮的三条教训**（比上面 8 条更值得记）：

1. **自检本身会有「从来不跑」的断言，而且它显示全绿。** 第 2 条是这轮最贵的发现：
   `check(` + `async` 组合下，同步的 `process.exit` 会在那个 async 体跑完**之前**发生。
   实测把它改回 `check`、在块末尾放一个写文件的标记，文件根本没被创建，而退出码是 0。
   → 凡是 `checkAsync`，改完都要问「它真的跑了吗」。
2. **负向验证不红 ≠ 代码没问题，也可能是测试没盖到那一段。** 第 6 条第一版只测
   `decideRunOutcome` 和记录落盘，而这两处都是**直接收到 `noEvents`** 的 —— 把
   `summarizeEvents` 里算 `hasAnyEvent` 的那行改成恒 `true`，照样全绿。补上
   `summarizeEvents` 自身的断言才变红。第 8 条同病：只测纯函数时，把**接线**还原不会
   变红（前提就是错的），补了一条「传 1ms 必须等满 40ms」才验到接线。
3. **同一类错会在相邻的地方各犯一次。** 第 4 条（触发时不查天花板）和第 8 条
   （`turnStartTimeoutMs` 只在一处校验）是同一个形状：**校验只补了一半**。修法都是
   「收口到一个函数、所有入口都走它」。

**改过的判据（§6.2）**：初稿写的「缺 `turn/end` 就算失败」和实现相反，实现按
「判成功 + 留证据」——这轮把文档改成和实现一致（见 §6.2 那段）。

### 13. 三档审查查出来的问题（第 3 轮修复，2026-10-06）

§12 那批修完，三档审查又各跑了一遍（L1 正确性用 `tier-std`、L2/L3 用 `tier-power`）。
三份结论都确认了核心修复的判据没写反（`hasAnyEvent === false → noEvents`、
`scheduled !== true && nextRunAt > now` 才早退）、两道天花板同源、手动早退**不丢写**
（`writeFile` 在 mutate 回调返回之后执行，`lastRunAt` 照常落盘）。
下面 3 个提交是查出来的问题，**一条一件事**：

| # | 缺陷 | 危害 | 提交 |
| --- | --- | --- | --- |
| 1 | 「配置不可信」这条缝只补了 `turnStartTimeoutMs` 一个字段 | 插件配置那一路不过 `SCHEDULER_FIELDS`：`maxConcurrent: NaN` → `running.size >= NaN` 恒假 → 并发不限、无界起真会话；`null` → 恒真 → 一个都不触发；`historyLimit: NaN` → `runs.json` 无界增长；`runTimeoutMinutes: 1e9` → 单轮占着名额 24.8 天，且 `staleRunMs` 被抬到几千年、时间兜底等于没有 | `227146c` |
| 2 | `scheduler_list` 的「上次跑成什么样」有四个洞 | 缺 `interrupted` 标签 ⇒ 把「进程被杀留下的那条」吐成英文原文；`noEvents` 只写进 summary 文案 ⇒ 列表里「零事件」和「有事件但没收尾」报同一句话，正是 §12 第 6 条要分开的两种；时间戳来自任务、结论来自 `runs` ⇒ 记录被裁掉后只剩时间戳，读的人当成干净成功；`runs.json` 混进一个 `null` 就让整个工具抛 | `a1562a9` |
| 3 | 手动触发之后的 `nextRunAt`，文案与实现相反 | `scheduler_update` 的注释是「为什么要报 `nextRunAt: null`」的依据，依据已被 `98ac5ff` 推翻；用户看到的「会在这一轮跑起来时按计划重算」同样不成立 | `e315f74` |

第 1 条的修法是**在共享处收一次**，不是继续给单个字段打补丁：装配时整份 `cfg` 过一遍
`SCHEDULER_FIELDS`（非法即回落默认），数值字段一律补上界（并发 64 / 单轮 24h / 记录
10 万条 / 任务 5000 / 取消等待 10min / 心跳 1h），`staleRunMs` 自己夹住入参（它是导出
函数，不能假设 `config` 已校验）。同时 `createExecutor` 入口就归一化启动窗口 —— 日志
（`:1093`）和结论文案（`:857`）报的是传进来的原值、实际等的是归一化值，配成 `NaN` 时会
说「NaNms 内没观察到这一轮启动」，又是一次「报出没发生过的数字」。

**这轮的教训**（接 §12 第 3 条）：

> **同一个形状的错，要把这一类都扫一遍，而不是修掉被指出的那一个。**
> §12 第 3 条已经写下「校验只补了一半」，可紧接着这一轮又只补了 `turnStartTimeoutMs`
> 一个字段 —— 同一个判断失误在相邻位置又犯一次。判据：改完一个校验点，问一句
> 「**还有谁走的是同一条缝**」，把那条缝本身堵掉（这里是「整份配置过一遍」）。

**查了但决定不改的**（已写进 §7，不是漏了）：`permissionRank` 对缺失 `permission`
按最严处理（改成宽松反而危险）；`run_now` 无限速（起会话能力本身的下界）；天花板只在
手动 `trigger` 拦而不在 `tick` 拦 —— executor 在 `agents.create` **之前**也会拦
（`lib/scheduler.js:953`），超限的存量任务到点**不会起会话**，只留一条 failed，
所以这是**不对称，不是漏洞**。

### 14. 再跑一遍三档审查（第 4 轮修复，2026-10-06）

按「修完重跑该层」，§13 那批修完之后 L1（正确性）和 L3（安全）各又跑了一遍。
L1 确认三处改动的意图都真做到了（`enabled:false` 走的是 `ok === undefined` 判断、
不会被误回落；FIELDS 与 DEFAULTS 的键完全同集，12/12 不存在 `cfg[key] = undefined`
的路径；`budgetMs` 三处口径一致）；L3 确认那四类非法值确实收口了、夹取顺序幂等、
归一化结果没有写回盘、超天花板的存量任务到点不起会话。**两轮共 4 个提交**：

| # | 缺陷 | 危害 | 提交 |
| --- | --- | --- | --- |
| 1 | 被拒/被回落的值**一个字都不说** | `tickMs` 配成 2 小时会静默变 1 秒（触发频率差 7200 倍），配置人只会觉得「我明明配了」而去找别的原因。文件那一路是 `readJsonConfig` 只返回「采纳了哪些」、被丢的值它不说；插件 config 那一路连日志回调都是 `() => {}` | `4ceee2d` |
| 2 | 上界只按**条数**定，没按「条数 × 单条上限」估 | `historyLimit: 100000` × 单条 `summary` 4000 + `error` 2000 字符，而 `mutateRuns` 每次整份读改写 ⇒ GB 级 `runs.json`、每跑完一个任务重写一遍；`maxTasks: 5000` × `prompt` 20000 字符同理；`tickMs` 下限 100ms 意味着每秒 10 次全文件解析 | `d090067` |
| 3 | 同上一条的邻类：`override` 里白名单外的键原样留进 `cfg` | 今天无读取点（静默 no-op），但留着就是「将来加一个读取点即绕过校验」；拼错的键名走同一个洞 | `d090067` |
| 4 | `scheduler_list` 对 `noEvents` **硬写**「成功」，不看 `run.status` | `runs.json` 是会被手改（也会被老版本写）的输入，出现 `failed + noEvents` 时把假话报给 agent。同一状态在面板叫「被打断」、服务端叫「被中断」 | `74d4aff` |

第 1 条的修法同样是**在共享处收一次**：`readJsonConfig` 报「值在文件里但没被采纳」
（只报配错、不报没配 —— 否则合法配置和空文件都刷屏），`layered()` 改成
`makeLayered(ctx)` 把 `ctx.logger.warn` 真的接下去（以前传的是 `() => {}`，等于留痕
空转），13 个调用点一个字没改。第 2 条把上界重定成 `historyLimit` 2000、
`maxTasks` 500、`tickMs` 下限就是默认值 1000ms。

**这轮的教训**（接 §13）：

> **收口之后要问「还剩什么乘积没算」**：上一轮堵的是「值非法」，合法值之间相乘
> （条数 × 单条大小 × 重写频率）依然能失控。校验一个数值上界时，要看它乘上什么
> 才是真正的资源占用。

**新增的可执行断言**：`SCHEDULER_DEFAULTS` 的每个默认值都必须**过得了自己的校验**
（否则装配时整份过 FIELDS 会把默认值悄悄换掉，一种不会被换红的失败形状）；
留痕那两处各有负向验证（把 `layered` 的 warn 换回 `() => {}` → 红；
去掉 `readJsonConfig` 的留痕 → 红）。
