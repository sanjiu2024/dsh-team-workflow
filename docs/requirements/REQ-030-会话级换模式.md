# REQ-030 · 会话级「换模式」（进行中的会话改 agent preset）

- **状态**：已完成（方案 B，2026-10-31）
- **对应版本**：待定（加能力 → minor）
- **提出**：2026-10-31，用户原话「现在每个会话无法修改模式，添加一个功能是修改每个会话的模式」

---

## 1. 要做什么

让**已经存在的会话**能换模式（agent preset：团队模式 / 红队模式 / 档位子预设等），
而不是只能新建会话时选一次。

## 2. 为什么（不做的后果）

用户当前的体验是「建会话时选错模式 → 只能重开一个」，而重开会丢掉已经积累的上下文
（对话、黑板上未完成的事、刚读进来的文件结论）。模式又恰恰是**任务中途**才需要改的东西
（一开始写代码、中途转去演练）。

## 3. 现状与硬约束（侦察结论）

**宿主明确禁止已开始的会话换 preset**：

`@deepseek-ai/dsh-agent-preset-registry` 的 `select(agent, agentPreset)`
（`dsh-agent-preset-registry/lib/index.js:753-770`）第一件事是检查轮次边界：

```js
const boundary = this.owner.sessionProjections.stateOf(agent.session, "turnBoundary");
if (boundary !== void 0 && (boundary.openTurnStartSeq !== null || boundary.lastTurn > 0))
  throw new RemoteError("agent-preset/locked", "This session has already started", { … });
```

也就是说：

| 会话状态 | `agentPresets.select()` | 说明 |
| --- | --- | --- |
| 新建、还没发过一句 | ✅ 成功（并 append `agent-preset/selected` 事件） | 这条路已经能用，只是没有入口 |
| 已经开始过（`lastTurn > 0`） | ❌ 抛 `agent-preset/locked` | 宿主设计约束，不是 bug |

为什么宿主这么设计：preset 决定**工具面与 persona**，中途换会让同一份 transcript 前后两半
属于两个不同的工具集合 —— 历史里的 `tool_call` 在新工具面里可能根本不存在。

另外两条相关事实：

- `dsh-api-session-controller` 的 `fork({ sessionId, atSeq })` 只接「切到第几条事件」，
  **不接受 agentPreset**（`lib/index.js` 的 fork 实现里只有 `atSeq`）；fork 出来的新会话继承
  `turnBoundary.lastTurn > 0`，**同样被 locked**。
- 只有 `create`/`ensureSession` 那条路能带 `agentPreset`（`lib/index.js:365,697`）。

## 4. 候选方案

### 方案 A · 只做「未开始」的会话（最小、零风险）

- 会话头加一个「模式」下拉；仅当该会话 `lastTurn === 0` 时可点，选择后调
  `agentPresets.select(agent, id)`，成功即生效（第一次发消息就用新工具面）。
- 已开始的会话：下拉置灰，hover 说明「dsh 不允许中途换（agent-preset/locked），
  要换请用『换模式并继续』或新会话」。
- 成本：一条命令 + 一条路由 + 面板小改；**不改宿主**。
- 覆盖度：解决「新建后想改」，**不解决**「聊到一半想改」。

### 方案 B · 「换模式并继续」= 新会话 + 新预设 + 上下文交接（推荐）

复用本包已有的两块积木：

1. `lib/handoff.js`（写交接文档 → 建新会话 → 把未完成任务注入）；
2. `dsh-api-session-controller` 的 `create({ agentPreset })`。

流程：点「换模式并继续」→ 写一份交接（当前任务、已定结论、未完成项、关键文件与行号）→
用选中的 preset 建新会话 → 把交接文档塞进新会话第一条系统注入 → 旧会话归档（不删）。

- 成本：新路由 + 命令 + 面板；**要处理**「旧会话归档」「新会话首条注入」「失败回滚」。
- 覆盖度：**任何会话都能换**（包括聊到一半的），代价是**新会话**（历史不在同一个会话里）。
- 天花板：不是原地换 —— 旧会话的 transcript 留在旧会话，新会话靠交接文档接上。

### 方案 C · 改宿主解锁（不推荐）

打补丁把 `select()` 的 locked 检查去掉，让已开始的会话原地换 preset。

- 后果：同一 session 里前后两半属于不同工具面；历史里的工具调用可能在新工具面里不存在，
  模型会对着"自己没见过的工具"继续推理。**这是宿主刻意拦的东西，破了只会得到更难查的错。**
- 除非用户明确要这个（并且接受"历史可能对不上"），否则不做。

## 5. 验收标准（按选定方案填）

- [ ] 未开始的会话：`/preset use redteam` 后第一次发消息，工具面是红队的（`redteam_*` 可见）
- [ ] 已开始的会话：同一条命令返回可读的拒绝理由（含 `agent-preset/locked` 原文与替代做法），不抛栈
- [ ] 方案 B：换模式后新会话第一条系统注入含交接文档、旧会话被归档且可恢复
- [ ] `npm test` 全绿（新增断言进 `selftest-purge.mjs` 或新 `selftest-preset-switch.mjs`）

## 6. 需要用户拍板的事

1. 选 **A**（只允许未开始会话，简单、零风险）还是 **B**（任何会话都能换，但是新会话 + 交接）？
2. 若选 B：旧会话**归档**还是保留在列表里（不归档会让人分不清哪个是"现在的"）？
3. 入口放哪：会话头工具区（本包小队入口那排）还是侧栏设置？

## 7. 天花板

- 无论哪个方案，**已开始会话的原地换模式**都不会做（除非选 C 并接受后果）。
