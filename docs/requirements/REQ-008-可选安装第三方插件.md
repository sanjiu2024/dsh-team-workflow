# REQ-008 · 装工作流时可选安装三个第三方插件

- **状态**：已完成
- **对应版本**：`1.11.1 → 1.12.0`（加能力 minor）
- **提出**：2026-10-06，用户原话——「在装这个工作流的时候可选安装
  `https://github.com/omdsh-dev/DSH-better-sidebar`、
  `https://github.com/elysia395/dsh-wallpaper-engine`、
  `https://github.com/PC2005-cloud/dsh-pet` 这三个插件」

澄清两问的答复（2026-10-06）：

1. **安装形态**：交互式逐项询问（默认全选否）；非交互环境自动跳过询问，可用 flag 预答。
2. **装不上的处置**：只警告，主流程继续，最后汇总；退出码仍为 0，并打印可重试的命令。

---

## 1. 要做什么

`dsh-team install` 把工作流装进某个 dsh profile 之后，**问一句**要不要顺带装这三个插件。
逐个问，默认答否；答是的那个当场装进同一个 profile，装完打印汇总与「重启 dsh 后生效」。

装完才想装的用户，用 `dsh-team plugins` 再问一遍同一套问题（不是重新装工作流）。

`dsh-team status` 里能看出这三个各自是装了还是没装。

## 2. 为什么（不做的后果）

用户明确要求了这件事，而且是**可复制性的问题**：这三个插件的装法不在同一处
（一个 npm 名带 `dsh-` 前缀、一个中间多一层 `plugin-`、一个仓库根目录根本没有
`package.json`），靠人记很容易装错版本 —— 而装错版本会被 dsh 启动预检**静默禁用**
（见 §5），用户只会觉得「装了没反应」。把三个名字、装机命令、许可注意事项固化在
一处，比写进 README 让人手抄可靠。

## 3. 不做什么

- **不改变三个插件的任何代码**，也不 fork / vendor 它们：只是替用户跑
  `dsh plugin … add <名字>`，装的是 npm 上的包。
- **不做卸载**（`--remove`）。要卸的人用 `dsh plugin --profile <p> remove <名>`
  ——汇总里会把这行打出来。
- **不动已在装的同名插件**：profile 里已经有 `dependencies[<名字>]` 时（例如本机 web
  profile 里已有 `dsh-better-sidebar@0.24.1`），交互式询问直接跳过并报「已装 x.y.z」；
  只有用户**显式点名** `--with-<key>` 才升级到 `@latest`。
- **不装到非 web profile**：这三个都是 `platform: "web"` 的界面插件，profile 的
  `bundles` 里没有 `@deepseek-ai/dsh-web-app` 就整体跳过并说明原因。
- **不代用户接受许可条款**：`dsh-pet` 的素材条款是「禁商用 + 二创须署名」（见 §5），
  交互询问的说明里给链接，装不装由用户定。
- 不引第三方依赖：`lib/profile-plugins.js` 只用 node 内置的 `node:readline`（在 bin 里用）。

## 6. 方案

**拆成「决定」与「动作」两半**，决定那半是纯函数、能被自检直接验：

### 6.1 新增 `lib/profile-plugins.js`（纯函数，零依赖）

- `OPTIONAL_PLUGINS`：三个条目，字段 `{ key, name, repo, what, need, note }`。
  `key` 就是 flag 后缀（`--with-sidebar`）；`repo` / `need` / `note` 是要打给用户看的
  仓库地址、版本要求、许可注意。
- `pluginDecisions({ profilePkg, flags, interactive })`
  → 每个插件一个 `{ key, name, action: "install" | "skip" | "ask", reason }`，判据顺序：
  - profile 的 `bundles` 里没有 `@deepseek-ai/dsh-web-app` → 三个全 `skip`
  - `--no-plugins` → 三个全 `skip`
  - 每项：`--without-<key>` → `skip`；`--with-<key>` → `install`（已装时 reason 写「升到最新」）
  - 已在 `dependencies` 里且没表态 → `skip`（reason = `已装 <version>`）
  - 没表态：交互**且这次没点过任何名** → `ask`；否则 `skip`（reason 分别写
    「这次只按点名的来」/「非交互环境不询问」）
- `withPluginBundles(profilePkg, names)` → 返回补好 `dsh.profile.bundles` 的新对象
  （幂等：没变化就返回**同一个**对象，调用方据此决定要不要写盘；不动别的字段、不改入参）。
- `installedVersions(profilePkg)` → 从 `dependencies` 取已装表（`cmdStatus` 也用它，
  免得「装没装」有两套口径）。
- `repoMatches(pkgJson, repo)` → 装完读一眼包自己的 `repository` / `homepage`，
  判断是不是表里那家（防同名抢注包）；两种写法都认（完整 URL 与 `github:a/b` 简写），
  包里没写来源时返回 `true`（不误报）。
- `unknownPluginFlags(flags)` → 认不出的 `--with-xx` / `--without-xx`（含 `--with-` 这种
  空后缀），在**动手装之前**由 CLI 报错退出。
- `pluginAddArgs(profile, name)` / `retryCommand(profile, key)` / `summarizePlugins(rows, profile, { dryRun })`
  → 命令形态与汇总行（`装了 x@1.2.3` / `跳过：已装 1.2.3` / `失败：<原因>；重试：…` /
  `要卸掉：dsh plugin --profile <p> remove <名…>`；dry-run 一律说「会装」不说「已装」）。

### 6.2 `bin/dsh-team.mjs`（动作那半）

- `cmdInstall`：写完 profile package.json 之后调 `installOptionalPlugins()`；
  **失败只记进汇总**，不 `fail()`（退出码保持 0）。唯一例外是开头读 profile 自己那份
  `package.json`：那份坏了是环境坏了（dsh 也加载不了），照旧直接报错退出 —— 这里若改成
  「当没有 web 界面」，用户看到的是「不装插件」而不是「你的 profile 坏了」。
- 新子命令 `plugins`：对已装好的 profile 跑同一套询问（`--with-…` / `--without-…` /
  `--no-plugins` / `--dry-run` 都照旧）。
- `cmdStatus`：加一段「可选插件」，逐行 `已装 <version>` / `未装`。
- `help`：补 `plugins` 一行 + 三个 flag。
- 询问用 `node:readline`，只在 `process.stdin.isTTY === true` 时问；否则按 §6.1 的
  「非交互」分支跳过。
- 装的动作：`dsh plugin --profile <p> add <name>@latest` → **先**验
  `node_modules/<name>` 在（不在就只记一条 failed，绝不往下走）→ 读回 profile
  package.json（读不到、或读到的不是对象也**不写**）→ `withPluginBundles` 补 bundles
  （有变化才写）。

### 6.3 为什么不用别的路

- **不用 `pnpm add`**：dsh 的 `plugin` 子命令已经把 profile 目录、`initProfile`、
  hoisted linker 都处理好了，自己拼 pnpm 要重做这些。
- **不在安装时直接改 `dependencies` 写死版本**：拿不到「最新版是多少」而不查 npm
  （不想为这个引网络请求 + 版本比较逻辑）；交给 pnpm 自己解析并写回。
- **dsh 那边是 `dsh plugin add`（转发 pnpm），本包只管把 bundles 补齐**：包只在声明了
  `dsh.bundle.patch` 时才会被 dsh 自动追加，与其假设，不如装完读回来自己补一次。
- **不做「装完自动启用/改配置」**：这三个插件各自的界面开关属于它们自己的事，
  我们只负责让包出现在 profile 里。

## 7. 天花板（做完之后仍不支持的）

- 不装/不卸（卸载只给命令提示）。
- 不检查「npm 上的最新版是否兼容本机 dsh」：只依赖 dsh 自己的启动预检，装错版本会被
  静默禁用 —— 汇总里会把「重启后看不到效果就查版本兼容」这句打出来。
- 不处理 `dsh-pet` 的 Electron 透明窗模式（那是它自己的配置，超出「装进 profile」）。
- 不替用户装 `ffmpeg`（wallpaper-engine 的帧率上限功能需要，缺了它自己会关）。
- 只在 `--profile` 指定的那一个 profile 里生效，不做多 profile 批量。
- 写 `profile/package.json` 是**整文件重排 + 非原子写**（`JSON.stringify(…, 2)` + `writeFileSync`）：
  字段不会丢（`withPluginBundles` 只 append），但用户自己排的 4 空格/tab 会被重排成 2 空格；
  中途断电可能留半个文件。既有三处同型写法（`bin/dsh-team.mjs` 的 install/uninstall/preset 路径），
  要改就一起改成 tmp+rename，别只改这一处。
- **打印出来给人复制粘贴的命令也是 sink**：`retryCommand`（`lib/profile-plugins.js`）与汇总里
  以及 `lib/profile-plugins.js` 里那两行 `要卸掉：…` 与 `重试：…` ——
  它们是唯一会被用户**原样粘进 shell** 的形态，下次收口时别只数 `run()` 那几处。
- `--profile` 的取值没有字符集校验，而它经 `quote()` + `shell: true` 转发给 dsh/pnpm
  （既有三处同型 sink：`bin/dsh-team.mjs:412 / :442 / :666` 的 `run("dsh", ["plugin", …, profile, "install"])`，
  这次只是又多一个：:300；行号截至本次提交）：profile 名里带 `;`、`&`、`$()` 会被 shell 解释。
  调用者就是用户自己，危害有限，但属于该收的口子 —— 单独开一次提交在**解析参数那一处**
  一起收（本 REQ 不动它，免得把这次改动和别的事搅在一起）。

## 9. 三层审查（首轮：L1 5 条 / L2 6 条 / L3 7 条）

L1 `tier-std`（正确性）、L2 `tier-power`（整体性）、L3 `tier-power`（安全）各跑一遍，
都给了 `文件:行号` + 修法。**没有 P0**。逐条处置：

| 来源 | 问题 | 处置 |
| --- | --- | --- |
| L1 P1 / L3 P1 | 先写 `dsh.profile.bundles` 再验 `node_modules/<name>`：包没落盘会留下指向不存在包的 bundle 项，dsh 启动会去加载它 | 调成**先验后写**，失败详情写明「没写 bundles」；自检加结构断言盯住这个顺序（这条路径真造不出来） |
| L1 P1 / L3 P2 | flag 校验在 `installOptionalPlugins` 内部，而 `cmdInstall` 先装完工作流才 await 它 → `install --with-pets` 装好了再 exit 1 | 抽出 `assertKnownPluginFlags()`，在两个命令**入口**就调；自检真跑 `install --with-pets` 并断言 profile 没被动过 |
