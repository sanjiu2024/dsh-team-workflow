## 11. 值得加的功能

从当天数字反推的能力缺口 —— 每条都挂了当天的证据，不是凭空想的：

### bash 结果的会话内缓存

- **证据**：`bash` 放大后约 64,881,026 tokens，占计费输入的 32.7%；同一会话内同一文件最多读 9 次，其中同参数重复 7 次
- **为什么值得**：工具结果留在上下文里，之后每一步模型请求都重新带上它 —— 同一份材料在同会话里读两次，就是把它在每一步都付两遍钱
- **现在就能做的**：缓存落地前：先 grep 定位再 read；read 带上 offset/limit，但同一区段别重读 —— 分页翻同一文件不同区段是正常的，浪费的是同一区段读两遍

### 模型等待监控与长 prompt 拆分

- **证据**：模型等待占步墙钟 77.0%（61,044,816ms / 79,270,137ms）；最慢一步 2,279,634ms，prompt 88,072 tokens
- **为什么值得**：时间大头花在等模型返回，而 prompt 越大等待越久 —— 削 prompt 就是直接削墙钟
- **现在就能做的**：先看最慢那几步的 prompt 里塞了什么，多半是几条超大工具结果

### 慢工具的超时与后台化

- **证据**：当天 10 次工具调用超过 10,000ms，最慢 2,266,960ms（`ask_user_question`）
- **为什么值得**：前台干等的慢调用会整段占住会话，而它往往是能后台化的长命令
- **现在就能做的**：长命令改用后台 job，先做别的再回来收结果

### 上下文水位护栏

- **证据**：单次峰值 prompt 131,343 tokens，已是窗口的 102.6%
- **为什么值得**：顶到窗口上限时压缩开始丢内容，而且越接近上限每一步越贵
- **现在就能做的**：先把折叠阈值下调一档，让它早一点触发

### rtk 包装兜底

- **证据**：rtk 合规率 59.7%（564/1399 条没走 rtk）
- **为什么值得**：没走 rtk 的命令输出是原始体积，直接进上下文
- **现在就能做的**：在 shell 层强制包装，别指望每次都想起来
