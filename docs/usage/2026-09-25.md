## 11. 值得加的功能

从当天数字反推的能力缺口 —— 每条都挂了当天的证据，不是凭空想的：

### read 结果的会话内缓存

- **证据**：`read` 放大后约 33,563,729 tokens，占计费输入的 42.7%；同一文件最多被读 47 次
- **为什么值得**：工具结果留在上下文里，之后每一步模型请求都重新带上它 —— 同一份材料读两次，就是把它在每一步都付两遍钱
- **现在就能做的**：缓存落地前：先 grep 定位再 read；read 一律带 offset/limit，同一文件一次读全

### 模型等待监控与长 prompt 拆分

- **证据**：模型等待占步墙钟 76.5%（10,470,819ms / 13,690,883ms）；最慢一步 197,732ms，prompt 43,622 tokens
- **为什么值得**：时间大头花在等模型返回，而 prompt 越大等待越久 —— 削 prompt 就是直接削墙钟
- **现在就能做的**：先看最慢那几步的 prompt 里塞了什么，多半是几条超大工具结果

### 慢工具的超时与后台化

- **证据**：当天 10 次工具调用超过 10,000ms，最慢 109,763ms（`ask_user_question`）
- **为什么值得**：前台干等的慢调用会整段占住会话，而它往往是能后台化的长命令
- **现在就能做的**：长命令改用后台 job，先做别的再回来收结果

### 上下文水位护栏

- **证据**：单次峰值 prompt 120,887 tokens，已是窗口的 94.4%
- **为什么值得**：顶到窗口上限时压缩开始丢内容，而且越接近上限每一步越贵
- **现在就能做的**：先把折叠阈值下调一档，让它早一点触发

### 联网搜索的查询缓存

- **证据**：同一组搜索词当天被搜了 4 次（`vue3`）；全天联网 15 次共 8,221ms
- **为什么值得**：重复搜索既是白花的网络时间，也是白花的上下文 —— 结果几乎一样
- **现在就能做的**：当天先复用上一次结果，别换着措辞反复搜
